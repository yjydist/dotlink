# Feature Specification: 声明式 dotfile 软链接管理

**Feature Branch**: `001-dotfile-link-management`

**Created**: 2026-09-14

**Status**: Draft

**Input**: User description: "我想要创建一个名称为 dotlink 的 Rust 项目. 这个项目专注于管理配置文件 (也称为 dotfile). 使用声明式配置文件把自己的 dotfile repo 中的 dotfile 软链接到正确的地方. 这个项目可以方便通过声明式配置文件方便的管理自己的配置文件. 把自己的配置文件集中到一个目录(仓库)下. 这样就可以把这个仓库方便的 push 到 remote repo 中来存储. 部署的时候也可以直接 clone 下来. 然后通过这个项目一键把配置目录软链接到正确的地方"

## Clarifications

### Session 2026-09-14

- Q: Windows 在首个版本中应该被完全排除 (在 Windows 上明确拒绝运行), 还是保留某种程度的支持? → A: 完全排除, 在 Windows 上明确拒绝运行并说明不支持, 不尝试创建任何链接.
- Q: 用户是否可以通过参数或环境指定清单位置与仓库根目录, 命令是否向上级目录搜索清单? → A: 都不可以.清单位置唯一固定为当前工作目录下的 `dotlink.toml`, 该文件所在目录即仓库根目录; 不向上搜索, 不提供任何相关参数或环境变量.用户的心智模型只包含"当前目录 + 该目录下的 `dotlink.toml` + 清单内声明的目标路径"这三样东西.
- Q: 只读命令 (preview 与 status) 在发现有待办事项时, 是否应该用退出码表达? → A: 应该.退出 0 当且仅当该命令所关心的期望状态已达成, 因此存在待执行动作或偏离时退出 1.代价是 `set -e` 脚本中裸调 preview 会中断, 需在帮助文本与文档中提示推荐写法.
- Q: 用户在清单中允许覆盖时, 该取值的名称是否应比 `backup` 更明确地表达"先备份再替换"? → A: 是.取值更名为 `replace_and_backup`, 使清单字面直接说明该条目的行为, 不需要读者额外了解"备份即意味着替换".

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 一条命令把仓库中的配置部署到目标位置 (Priority: P1)

用户已经在自己的 dotfile 仓库中集中保存了若干配置文件 (例如 shell 配置,编辑器配置), 并在仓库里写好了声明式清单, 说明"仓库中的哪个条目应该出现在目标系统的哪个路径".用户在新机器上 clone 仓库后, 执行一次部署动作, 所有声明的链接被创建到正确位置, 配置立即生效.

**Why this priority**: 这是产品的核心价值.没有它, 用户仍需手工执行一堆 `ln -s`, 集中管理的收益无法兑现.单独交付这一条就已经是一个可用的 MVP.

**Independent Test**: 在一个空目录中准备一份包含 2-3 个条目的清单与对应文件, 执行一次部署, 检查每个声明目标路径都变成了指向仓库内文件的链接; 随后修改仓库内文件内容, 确认目标侧读到的是新内容.

**Acceptance Scenarios**:

1. **Given** 一份声明了 3 个条目的清单且所有目标路径当前不存在, **When** 用户执行部署, **Then** 3 个目标路径都被创建为指向仓库内对应文件的链接, 且命令报告 3 个条目成功.
2. **Given** 一份清单已成功部署过一次, **When** 用户在未修改任何内容的情况下再次执行部署, **Then** 结果是幂等的: 不产生错误, 不破坏已有链接, 命令明确报告条目已处于期望状态.
3. **Given** 仓库中新增了一个条目并写入清单, **When** 用户执行部署, **Then** 只有新条目被创建, 已有条目保持不变.

---

### User Story 2 - 部署前预览将发生的变更 (Priority: P2)

用户修改了清单 (新增条目,改变某条目的目标路径), 但不确定这些改动会影响到什么.用户希望在真正改动文件系统之前, 先看到"将会创建什么,将会覆盖什么,哪些会冲突"的完整清单, 再决定是否执行.

**Why this priority**: 部署动作会写入用户主目录, 属于难以撤销的操作.一个可信的预览能力是用户敢于使用工具的前提, 但它依赖于 US1 已存在的部署语义, 因此排在第二位.

**Independent Test**: 构造一个包含"新条目"和"目标已被无关文件占用"两种情况的环境, 执行预览, 确认输出准确区分这两种情况且未对文件系统做任何修改.

**Acceptance Scenarios**:

1. **Given** 某条目的目标路径被一个普通文件 (非本工具创建的链接) 占用, **When** 用户执行预览, **Then** 输出将该条目标记为冲突并说明原因, 且文件系统保持不变.
2. **Given** 某条目的目标路径已是本工具创建的正确链接, **When** 用户执行预览, **Then** 输出将该条目标记为已是最新, 且文件系统保持不变.

---

### User Story 3 - 安全地处理已有文件 (Priority: P2)

用户的机器上已经存在某个配置文件 (例如手工编辑过的 `~/.bashrc`), 现在想改用仓库统一管理.用户希望部署时不会静默丢弃这份已有内容, 而是先把它保留下来 (备份), 再建立链接.

**Why this priority**: 丢失用户已有配置是不可接受的失败模式.它与 US2 同属"安全使用"范畴, 是让工具可以在真实机器上放心运行的必要条件.

**Independent Test**: 预先在目标路径放置一个含已知内容的文件, 使用允许备份的部署方式执行, 确认链接已建立,原内容在备份位置可读且完整.

**Acceptance Scenarios**:

1. **Given** 目标路径存在一个普通文件且用户允许备份, **When** 执行部署, **Then** 原文件被保留到备份位置, 目标路径被替换为指向仓库的链接, 命令报告备份发生的位置.
2. **Given** 目标路径存在一个普通文件且用户不允许覆盖, **When** 执行部署, **Then** 该条目被跳过并报告原因, 原文件保持原样, 其他无冲突条目正常完成, 命令以可区分的非成功状态结束.

---

### User Story 4 - 撤销部署, 让系统回到未管理状态 (Priority: P3)

用户想停止使用本工具管理某些配置 (可能想改回手工维护, 或想把整台机器恢复原状).用户希望撤销动作只移除本工具创建的链接, 恢复此前备份的原始文件, 而绝不触碰其他任何文件.

**Why this priority**: 是完整生命周期的一部分, 且有明确的安全价值 (可回滚), 但只有在部署能力稳定后才谈得上.

**Independent Test**: 在已部署 (且发生过一次备份) 的环境中执行撤销, 确认链接被移除,原始内容被恢复,其他文件与目录未被改动.

**Acceptance Scenarios**:

1. **Given** 某条目的链接由本工具创建且该条目曾有备份, **When** 用户执行撤销, **Then** 链接被移除且备份内容被恢复到原路径, 命令报告恢复动作.
2. **Given** 部署后用户手工把某个目标路径改成了一个真实目录 (非本工具创建), **When** 用户执行撤销, **Then** 该路径被跳过并报告原因, 目录内容未被删除.

---

### User Story 5 - 发现清单与实际状态的不一致 (Priority: P3)

用户在多台机器上使用同一份清单, 或手工改动过某些文件, 因此实际状态可能与清单声明不符.用户希望有一个只读的检查动作, 报告"哪些条目未部署,哪些指向了错误位置,哪些被外部修改", 以便决定下一步.

**Why this priority**: 提升可维护性与可信度, 但不阻塞核心流程.

**Independent Test**: 构造一个"部分部署,部分被外部破坏"的环境, 执行检查, 确认输出准确分类每种不一致且未修改文件系统.

**Acceptance Scenarios**:

1. **Given** 某个已声明条目在目标路径上不存在链接, **When** 用户执行检查, **Then** 该条目被报告为未部署.
2. **Given** 某个目标路径上的链接落在仓库之外 (非本工具创建), **When** 用户执行检查, **Then** 该条目被报告为"被非本工具创建的内容占用"而非"指向错误", 并给出该链接的实际指向; 用户据此知道这不是自己的配置写错了, 而是该路径被别的东西占着.
3. **Given** 某个目标路径上的链接由本工具创建 (指向仓库内) 但指向的源不对, **When** 用户执行检查, **Then** 该条目被报告为"指向错误"并给出实际指向, 用户据此知道需要修清单或重新部署.

---

### Edge Cases

- 清单中两个条目声明了同一个目标路径: 必须在执行任何文件系统改动之前拒绝整份清单, 并指出冲突的两个条目.
- 清单中两个条目声明了同一个源文件, 但目标路径不同: 属于合法用法, 应正常各自建立链接.
- 清单声明的源文件在仓库中不存在: 该条目标记为"源缺失", 不创建链接, 并以可区分状态结束.
- 目标路径的父目录不存在: 视为需要创建的目录并自动创建 (这是常见需求, 例如 `~/.config/nvim/` 尚未存在); 若创建失败则报告该条目失败, 不影响其他条目.
- 目标路径已是本工具创建的正确链接: 视为成功, 不重复操作, 不产生备份.
- 目标路径是符号链接但指向错误位置: 视为冲突, 需用户显式允许才可替换, 替换前对链接本身 (而非其目标) 做备份.
- 目标路径是目录 (而非文件): 默认视为冲突并拒绝自动处理; 用户显式允许时才可备份该目录并建立链接.
- 仓库中的条目本身是目录 (例如希望整目录软链接 `~/.config/nvim`): 应支持整目录软链接.
- 清单文件缺失,不可读或格式非法: 报告具体位置与原因, 不做任何文件系统改动.
- 目标路径包含相对路径或用户主目录简写: 按文档约定解析 (主目录简写展开为当前用户主目录); 报告中展示的 MUST 是**用户书写的原始字符串**, 便于用户对照自己的清单, 解析后的绝对路径不展示.
- 同一源文件在多次执行之间内容变化: 由于是软链接, 目标侧自动反映最新内容, 无需重新部署.
- 两个并发的部署动作: 应避免互相产生半完成的链接状态 (至少不得静默产生错误结果).
- 在不支持的操作系统上执行任何动作 (含只读的预览与检查): 在读取清单与做任何判定之前即以非成功状态结束, 说明平台不受支持, 不产生部分输出误导用户, 不修改文件系统.
- 用户在不含 `dotlink.toml` 的目录下执行命令 (例如在仓库的子目录中, 或完全在仓库之外): 直接以校验失败结束, 不向上搜索, 也不猜测清单位置.
- 执行命令时当前工作目录已被删除 (例如先 `rm -rf` 了仓库目录, 而 shell 的 cwd 仍指向其中): 与"清单不存在"同样是校验失败, 但说明指出"当前工作目录不可用", 使用户能区分"我站错目录了"与"仓库被删了".见 FR-015.
- 执行命令时未给出子命令, 或子命令拼错 (例如 `dotlink statu`): 在读取清单之前即以可区分的非成功状态结束, 说明中给出正确的子命令列表, 不修改文件系统.
- 判定某条目所需的文件系统读取失败且原因**不是**"路径不存在" (例如目标父目录不可进入, lstat 返回权限错误): 该条目标记为"无法判定", 计入失败并说明底层原因, 不阻断其余条目; 这既不是清单校验失败, 也不是"目标被占用". "路径不存在"是正常事实而非故障, 按未部署或源缺失归类.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 从一个用户可编辑的声明式清单中读取条目, 每个条目至少表达"仓库中的源条目"与"系统上的目标路径"两项信息.
- **FR-002**: 清单 MUST 支持主目录简写 (例如以 `~` 开头的目标路径) 并在解析时展开为当前用户的主目录.
- **FR-003**: 系统 MUST 提供部署动作, 依据清单在目标路径创建指向仓库内源条目的软链接.
- **FR-004**: 部署动作 MUST 是幂等的: 对同一清单与同一文件系统状态重复执行, 不产生额外改动,不报错, 并如实报告条目已处于期望状态.
- **FR-005**: 系统 MUST 支持在目标路径不存在时自动创建其缺失的父目录.
- **FR-006**: 系统 MUST 提供预览动作, 在不修改文件系统的前提下, 报告每条目将会发生什么 (新建,已是最新,冲突,源缺失), 且预览报告的判定与后续部署的实际行为一致.
- **FR-007**: 当目标路径已被非本工具创建的内容占用时, 系统 MUST 默认拒绝覆盖, 并报告该条目的冲突原因.
- **FR-008**: 系统 MUST 提供显式的覆盖许可方式 (清单条目级的 `replace_and_backup` 取值), 允许用户对冲突条目执行"备份现有内容, 再建立链接", 并在输出中报告备份位置.MUST NOT 提供命令行级的全局覆盖开关.
- **FR-009**: 系统 MUST 提供撤销动作, 仅移除由本工具创建的链接; 对存在备份的条目, 移除链接后将备份内容恢复到原路径.
- **FR-010**: 撤销动作 MUST 绝不删除或修改任何非本工具创建的路径 (含用户自己的外部链接); 遇到这类路径时 MUST 跳过该条目并报告原因, 且以可区分的非成功状态结束.
- **FR-011**: 系统 MUST 提供检查动作, 只读地报告清单与实际状态的不一致, 至少区分五类: 未部署 (`absent`), 指向错误 (`wrong`, 链接由本工具创建但指向的源不对), 被非本工具创建的内容占用 (`foreign`, 目标被本工具之外的链接,文件或目录占用), 源缺失 (`missing`), 已是最新 (`ok`). 其中"指向错误"与"被非本工具创建的内容占用"的划分依据是**链接归属**: 落在仓库根之内的链接算本工具创建, 之外的不算. 该动作 MUST 另有一个可区分的结局用于"判定所需信息无法读取"这一环境故障 (报告失败原因, 不归入上述任何一类).
- **FR-012**: 系统 MUST 能够判定"某个路径上的链接是由本工具创建的", 以此作为撤销与冲突判定的依据, 该判定不得依赖用户手工维护的状态文件.
- **FR-013**: 系统 MUST 在执行任何文件系统改动之前完成整份清单的校验, 至少包括: 同一目标路径被多个条目声明,条目缺少必需字段,目标路径无法解析.校验失败时不得产生任何改动.
- **FR-014**: 当单个条目的操作失败时, 系统 MUST 继续处理其余条目, 在结束时给出成功与失败的完整清单, 并以可区分的非成功状态结束.
- **FR-015**: 系统 MUST 把"当前工作目录下的 `dotlink.toml`"作为清单的唯一来源, 并把该文件所在目录作为仓库根目录; MUST NOT 向上级目录搜索清单, MUST NOT 提供任何指定清单位置或仓库根目录的参数或环境变量.清单不存在时视为校验失败.当前工作目录本身不可用 (例如该目录已被删除) 时同样视为校验失败, 但说明 MUST 指出"当前工作目录不可用", 而非"找不到清单" —— 二者的处置相同, 成因不同, 混淆会让用户去检查一个不存在的问题.
- **FR-016**: 系统 MUST 为每个条目输出人类可读的结果 (条目,动作,结果,涉及路径), 使输出足以支撑用户判断是否需要人工介入.
- **FR-017**: 预览,检查,部署与撤销四条路径 MUST 共享同一套条目判定规则, 保证同一状态下四者结论一致.撤销路径的"结论"指它据以决定"是否移除此链接"的那一项判定, 与其余三条命令同源.
- **FR-018**: 系统 MUST 支持两类源条目的处理并按类型正确处理: 源为文件时建立指向该文件的链接, 源为目录时建立指向该目录的**整目录**软链接 (即链接本身指向目录, 而非对其内容逐个建链). 本要求约束**行为**, 不要求输出中出现文件/目录的类型标签.
- **FR-019**: 系统 MUST 仅在受支持的操作系统上运行; 在不受支持的平台上 MUST 立即以可区分的非成功状态结束, 说明该平台不受支持, 且 MUST NOT 创建任何链接或修改文件系统.
- **FR-020**: 系统 MUST 用退出码区分下述四类结局: 命令关心的期望状态已达成; 存在待执行动作,偏离或条目级失败; 清单校验失败且未做任何改动; 平台不受支持.只读命令与写入命令 MUST 使用同一套退出码语义.**子命令缺失或拼错属于"调用方式错误"而非上述四类结局**: 系统 MUST 在读取清单之前拒绝它, 且 MUST 不修改文件系统; 它的码值与可区分方式是接口设计决定, 归属 `contracts/cli.md`, 本要求只约束"必须可区分且不修改文件系统".

### Key Entities *(include if feature involves data)*

- **清单 (Manifest)**: 用户编写的声明式文件, 固定为当前工作目录下的 `dotlink.toml`, 描述仓库中受管理的条目及各自的目标路径.是系统唯一的事实来源, 不包含全局默认值: 仓库根目录由它的位置唯一确定, 覆盖许可逐条目给出.
- **条目 (Entry)**: 清单中的一条声明, 包含源条目在仓库中的位置,目标路径,可选的条目级覆盖策略 (`skip` 或 `replace_and_backup`).
- **部署状态 (Deployment State)**: 某个条目在文件系统上的实际状况, 取值为八种: 源缺失,未部署,已是最新,指向错误,外部链接占用,外部文件占用,外部目录占用,无法判定 (判定所需的文件系统读取失败, 且原因不是"路径不存在").中间的"外部链接 / 外部文件 / 外部目录占用"三者在面向用户的报告中合并称为"被非本工具创建的内容占用 / 冲突占用", 但判定上必须区分出"是符号链接"这一情形, 因为它决定了撤销是否允许移除.由源条目在文件系统中的实况推导得出, 不依赖额外持久化记录.
- **链接归属 (Link Ownership)**: 判定某个符号链接是否由本工具创建的依据: 链接解析后的绝对路径落在仓库根目录之内.该判定完全由文件系统实况给出, 不需要任何状态文件, 它是"指向错误"与"被非本工具创建的内容占用"的分界线, 也是撤销动作的破坏面上界.
- **备份 (Backup)**: 被覆盖的原有内容在替换前保留的副本, 具有可被用户找回的位置.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 用户在一台已 clone 仓库的全新机器上, 使用一条命令即可完成全部已声明条目的部署, 无需手工执行任何链接创建操作.
- **SC-002**: 对同一清单连续执行两次部署, 第二次执行不产生任何文件系统改动.
- **SC-003**: 在包含 50 个条目的清单上, 预览与部署动作均在 2 秒内完成并输出逐条目结果.
- **SC-004**: 在目标路径已被占用的场景下, 部署动作 100% 不会静默丢弃原有内容: 要么保留到可定位的备份, 要么跳过该条目并报告.
- **SC-005**: 撤销动作在存在非本工具创建的路径时, 100% 跳过这些路径且不产生任何删除.
- **SC-006**: 预览报告的每条结论与随后实际部署的结果一致率 100% (不含预览之后人为修改文件系统的情形).
- **SC-007**: 用户仅凭命令行输出即可判断每个条目的结果与下一步动作, 无需额外查阅文档.
- **SC-008**: 一个从零开始的新用户, 在只阅读快速上手说明的前提下, 能在 5 分钟内完成"编写清单 → 预览 → 部署 → 验证链接生效"的完整流程.
- **SC-009**: 用户无需查阅文档, 即可从退出码区分"已符合期望""有待办或失败""清单有问题""环境不支持"四类结局, 并据此决定下一步动作.若所选工具链使"调用方式错误"与其中某一类共用同一码值, 则必须在**该命令自身的帮助文本**中说明二者的区分方式, 使用户仍能仅凭命令行输出作出判断.
- **SC-010**: 用户为了运行命令所需了解的环境只有一处: 存放 `dotlink.toml` 的那个目录.在文档中解释"命令该在哪里运行"所需的文字不超过一句话.

## Assumptions

- 目标用户是使用 Unix 类系统的开发者, 系统支持符号链接; 受支持平台为 macOS 与 Linux.Windows 属完全排除项, 而非"暂不完善": 在 Windows 上系统必须明确拒绝运行, 不尝试创建链接, 也不提供降级路径.
- 一个仓库集中保存该用户的全部受管配置文件, 仓库中的相对路径即为条目的源位置.
- 清单采用人类可读,便于版本控制中逐行对照的纯文本格式, 由用户直接手工编辑; 不需要额外的图形界面或生成向导.
- 默认按"单用户"使用: 目标路径解析基于执行命令的当前用户主目录, 不处理多用户或需要提权的系统级路径 (如 `/etc`) 写入.
- 备份默认保存在被覆盖路径同一目录下的带固定后缀与时间戳的相邻位置, 以便用户就近找回; 不引入集中的备份仓库.
- "本工具创建"的判定以链接目标是否落在仓库根目录内为依据, 因此不需要额外的状态数据库; 用户把仓库目录整体移动后需要重新部署.
- 冲突的默认策略为"拒绝", 覆盖必须由用户在清单中按条目显式许可 (`replace_and_backup`), 不做任何交互式询问, 以支持在脚本与自动化环境中使用.
- 清单位置与仓库根目录不存在配置面: 命令必须在含 `dotlink.toml` 的目录下执行.用户需要记住的只有这一个约定, 不再有"清单在哪,仓库根在哪"的额外问题, 也没有可能互相矛盾的多个来源.
- 撤销是条目级可选择的: 用户可以只撤销部分条目, 也可以整份清单撤销.
- 部署动作不负责从远程 clone 仓库, 也不负责 Git 操作; 仓库的获取与版本管理由用户自行完成.
- 首个版本不包含: 配置模板渲染/变量替换,加密敏感文件,跨机器差异化管理,自动检测已有配置文件并反向生成清单,Windows 平台支持 (明确拒绝运行).
