# Phase 1 Data Model: 声明式 dotfile 软链接管理

本工具没有持久化数据模型 (无数据库,无状态文件).以下"实体"全部是解析与判定的**内存表示**, 以及一个由文件系统实况推导出的状态枚举.唯一写入磁盘的产物是备份文件 (见 `Backup`).

---

## 1. Manifest (清单)

用户编写的声明式文件, 是系统唯一的事实来源.

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `entry` | `[Entry]` | 是 | 条目数组.定义为 `[[entry]]` 数组表.至少 1 个条目 |

**位置**: 当前工作目录下的 `dotlink.toml`.不向上搜索父目录.该文件所在目录 == 仓库根目录, 由位置唯一确定; 不存在指定清单位置或仓库根目录的参数或环境变量.

**校验规则** (对应 FR-013, 全部在**任何文件系统改动之前**完成):

| 编号 | 规则 | 违反时的后果 |
|------|------|--------------|
| V-1 | 清单文件存在且可读 | 整体拒绝, 退出码 2 |
| V-2 | TOML 语法合法 | 整体拒绝, 报告出错位置与原因, 退出码 2 |
| V-3 | `entry` 非空 | 整体拒绝, 退出码 2 |
| V-4 | 每个条目 `source` 与 `target` 均非空 | 整体拒绝, 指出条目下标, 退出码 2 |
| V-5 | 不存在两个条目声明**同一个目标路径** (比较非严格规范化后的绝对路径, 见 3.1 的"悬空链接"; **不得**用 `Path::canonicalize` -- 待部署的目标路径通常尚不存在) | 整体拒绝, 指出冲突的两个条目下标, 退出码 2 |
| V-6 | 每个条目的 `target` 可解析为绝对路径: `~/...` 与裸 `~` 展开为主目录, 绝对路径原样, 相对路径可挂到仓库根; 其他以 `~` 开头的形态 (如 `~.bashrc` / `~foo/bar`) 一律拒绝 | 整体拒绝, 指出条目下标与原因, 退出码 2 |
| V-7 | `on_conflict` 取值属于 `{skip, replace_and_backup}` | 整体拒绝, 指出条目下标与非法值, 退出码 2 |
| V-8 | 只出现已定义的键: 顶层仅 `entry`, 条目内仅 `source` / `target` / `on_conflict` (见 `contracts/manifest.md`) | 整体拒绝, 指出键名与所在层级, 退出码 2 |
| V-9 | `target` 归一化后不得退化为文件系统根 `/`、当前用户主目录 (裸 `~` 或书成绝对路径的等价形态)、仓库根本身或其祖先 (如 `.` / `..`) -- 这些落点一旦被替换备份, 毁掉的是整个目录、整个主目录乃至源仓库 | 整体拒绝, 指出条目下标与书写形态, 退出码 2 |
| V-10 | `target` 归一化后不得与**本条目**的 `source` 相同 (自指链接恒为断链; **跨条目**的重合不属自指, 不做校验, 由判定阶段的状态暴露) | 整体拒绝, 指出条目下标与书写形态, 退出码 2 |

**注意 V-4 与源文件存在性的区别**: 源条目在仓库中不存在**不是**校验错误, 而是条目的运行时状态 `SourceMissing`.原因是这一条可以在部署之间被用户单独修复 (例如先补文件再部署), 让它整体拒绝会强迫用户同时修好所有条目.而 V-1 到 V-10 属于清单本身的缺陷, 无法在保留清单其余部分的前提下有意义地继续.这个区分对应规格中"整份清单校验"与"单条目失败不阻塞其余条目" (FR-014) 的分工.

**允许的重复**: 两个条目声明**同一个源条目**但目标路径不同 —— 合法 (规格 Edge Cases 明确要求).

## 2. Entry (条目)

| 字段 | 类型 | 必填 | 默认 | 说明 |
|------|------|------|------|------|
| `source` | 字符串 | 是 | — | 源条目在仓库中的相对路径 (不接受 `~` 前缀或绝对路径).可为文件或目录 |
| `target` | 字符串 | 是 | — | 目标路径.支持 `~` 前缀与相对路径 (见 `research.md` R5) |
| `on_conflict` | 枚举 `skip` \| `replace_and_backup` | 否 | `skip` | 目标被非本工具内容占用时的策略 |

**解析产物** (由 `entry.rs` 计算, 不再回写清单):

| 字段 | 类型 | 说明 |
|------|------|------|
| `source_path` | 绝对路径 | 仓库根 + `source`, 已规范化 (非严格 `os::normalize`) |
| `target_path` | 绝对路径 | 按 R5 规则解析并规范化 |

**两侧都必须过 `os::normalize`**: 只规范化 `target_path` 而让 `source_path` 保留字面形态, 会使 3.1 的 `L == S` 判定在两种常见情形下失败 -- (1) `$PWD` 与清单中的相对 `source` 拼出的路径含多层 `..` 或符号链接段 (例如仓库根经 `/tmp` 别名形态取得, 或从含 `..` 的路径进入); (2) 仓库根目录本身处于一条含符号链接的路径下. 由于 `L` (链接文本解析后) 与 `R` (仓库根) 都经规范化, `S` 若不过同一函数, 比较两侧的语义就不一致, 重新引入 `research.md` R2 的规范化陷阱. 归属判定 (`link_is_inside_repo`) 与此处必须以**同一个** `os::normalize` 为基准.

**不设 `source_kind` 字段**: FR-018 要求目录条目建立**整目录**软链接, 而 `symlink(P, S)` 对文件与目录是同一个调用, 无需区分 -- 目录是否被整体链接由链接指向的对象本身决定, 不由额外字段决定.类型标签也明确不进入 token 与说明措辞 (FR-018).因此该字段在所有命令中均无消费者, 计算它只会多一次 `symlink_metadata` 与一个无用的公开接口 (违反宪章第一条"接口是成本"); 若将来出现确实依赖源类型的判定, 在**那时**随该判定一并引入, 而不是现在预留.

## 3. EntryState (条目状态)

由 `classify` 从"解析后的 Entry + 文件系统实况"推导, 是**唯一**的判定出口 (FR-017).

### 3.1 现状枚举 `Current`

`L` 记 `target_path` 上的符号链接文本解析并规范化后的绝对路径; `S` 记 `source_path` 规范化后的绝对路径; `R` 记仓库根规范化后的绝对路径.

| 取值 | 判定条件 (两次 `lstat` 均成功时按此顺序求值, 首个命中者胜出; 求值语义见下方) | 输出措辞 |
|------|------------------------------------------|----------|
| `SourceMissing` | `source_path` 不存在 | 源缺失 |
| `Absent` | `target_path` 不存在 (含其父目录不存在) | 未部署 |
| `LinkedCorrect` | `target_path` 是符号链接, 且 `L == S` | 已是最新 |
| `LinkedWrong` | `target_path` 是符号链接, 且 `L` 落在 `R` 之内, 但 `L != S` | 指向错误 |
| `ForeignLink` | `target_path` 是符号链接, 且 `L` 落在 `R` **之外** | 冲突占用 (非本工具创建) |
| `ForeignFile` | `target_path` 存在且**不是**符号链接, 是文件 | 冲突占用 |
| `ForeignDir` | `target_path` 存在且**不是**符号链接, 是目录 | 冲突占用 |
| `Unreadable` | **不参与本表的顺序求值**: 源侧或目标侧的 `lstat` 失败且错误**不是** `NotFound` (例如父目录不可进入的 `EACCES`) 时直接得出, 详见下方"求值语义" | 无法判定 |

**求值语义 (两次 `lstat` 与 `Unreadable` 的优先权)**: 上表"判定条件"一列描述的是路径的**确定事实**, 因此它只覆盖 `lstat` 成功返回的情形. 实现必须对**源侧** (`source_path`) 与**目标侧** (`target_path`) 各做一次 `lstat`, 并按下述规则裁决:

1. 任一次 `lstat` 失败且错误**不是** `NotFound` -> 该条目为 `Unreadable`, 说明中给出底层错误与失败的那一侧 (源侧 / 目标侧). 该结论**先于**表中所列各行: 它不是"某个条件命中", 而是"某些行的条件根本无法求值".
2. 源侧 `lstat` 返回 `NotFound` -> `SourceMissing` (第 1 行).
3. 目标侧 `lstat` 返回 `NotFound` -> `Absent` (第 2 行).
4. 两次 `lstat` 均成功 -> 从第 3 行起自上而下取首个命中者.

因此"自上而下取首个命中者"这一顺序约束在**两次 `lstat` 均成功**的前提下严格成立; `Unreadable` 是这一前提被破坏时的**唯一**出口, 而不是表末的一个兜底分支. **不得**把非 `NotFound` 的失败读作"路径不存在"从而落入 `Absent` / `SourceMissing` -- 那会把一次环境故障伪装成一个确定的文件系统事实, 与 FR-011 要求的可区分结局直接冲突.

`Unreadable` 不属于"清单缺陷" (V-1 到 V-10 只在解析阶段校验清单本身), 也不属于"条目被占用", 而是**判定阶段的环境故障**: 该条目无法被归类为一个确定的文件系统事实. 它必须:

- 使该条目的 token 为 `fail` 并计入汇总的"失败"列, 并在说明中给出底层错误 (`contracts/cli.md` 的 `fail` 行放宽为"出现于任何命令", 见该表).
- 使退出码为 **1** (存在未达成目标的条目), 而非 2 (清单校验失败) 或 3 (平台不支持).
- 不阻断其余条目: 与 `fail` 的既有语义一致 (FR-014), 单条目失败不中断其余条目.

`NotFound` 是**正常路径**而非故障: 它对应"路径不存在"这一确定事实, 按上表归入 `SourceMissing` (源侧) 或 `Absent` (目标侧), 不得归入 `Unreadable`.

`LinkedWrong` 与 `ForeignLink` 的划分依据是**链接归属** (`research.md` R2), 而非"是否看起来指向正确" -- 二者互斥且穷尽所有符号链接情形:

- `LinkedWrong` 是"**我的**链接指错了地方" (用户改了清单中的 `source`, 或仓库内文件被移动). 它是 dotlink 自己的产物, 因此 `undo` 会移除它, `replace_and_backup` 会备份该链接本身.
- `ForeignLink` 是"**别人的**链接" (`L` 在仓库之外). 它不是 dotlink 的产物, 因此 `undo` 必须 `skip` (FR-010), 部署时视为冲突 (FR-007).

**判定顺序的理由**:
- `SourceMissing` 必须最先判定 -- 源不存在时无论目标侧状态如何都无法建立有意义的一致性, 且继续往下判定会给出误导性的"已是最新"或"冲突".
- 判定必须使用 `symlink_metadata` (即 `lstat` 语义) 而非 `metadata`, 否则对符号链接会穿透到其目标, 使 `ForeignLink` 与 `LinkedWrong` 无法区分.

**悬空链接的处理 (实现陷阱)**: `L` 与 `S` 都可能指向不存在的路径 (链接悬空, 或源条目本就缺失). Rust 的 `Path::canonicalize` 在这种情况下返回 `Err` (实测已确认), 因此**不得**直接用它做相等判定 -- 否则一个指向仓库内但已失效的链接会被误判为 `ForeignLink`, 进而导致 `undo` 拒绝清理自己创建的悬空链接. 两条绝对路径的比较必须采用**同一套非严格 realpath** 语义 (`os::normalize`, 见 `research.md` R2 的 Decision), 使悬空链接仍能被正确归类.

**`os::normalize` 的两段语义**: (1) 路径中**已存在**的段, 若为符号链接则解析其文本并继续 (macOS 上 `/tmp` -> `/private/tmp`,`/var` -> `/private/var`), 因此别名形态与物理形态的同一路径会落到同一个字符串; (2) **不存在**的尾段按词法规整 (逐段消除 `.` 与 `..`, 不再访问文件系统). 第一段是"别名形态的链接仍归本工具创建"所必需 -- 若只做词法规整, `/tmp/...` 的链接文本与 `/private/tmp/...` 的仓库根永不判等, 一条本工具创建的链接会被误判为 `ForeignLink`; 第二段是悬空链接可归类所必需. 二者不可只取其一, 且**都不得**改用 `Path::canonicalize`.

**输出措辞是一回事, 输出 token 是另一回事**: 上表的"输出措辞"是给人读的说明文字 (可调整).机器可断言 token 由 `(命令, Current, Action)` 三元组唯一决定, 由 `contracts/cli.md` 的"状态 token 表"**唯一**给出.同一 `Current` 在不同命令下可以是不同 token (例如 `Absent` 在 `apply` / `preview` 为 `create`, 在 `status` 为 `absent`, 在 `undo` 为 `ok`; `ForeignLink` 在 `preview` / `apply` 为 `conflict` 或 `replace`, 在 `status` 为 `foreign`, 在 `undo` 为 `skip`).实现时不得在 `render.rs` 里另起一套 token 命名.

### 3.2 动作映射 `Action`

| `Current` | `on_conflict` | `Action` | 副作用 |
|-----------|---------------|----------|--------|
| `SourceMissing` | — | `ReportMissingSource` | 无 |
| `Unreadable` | — | `ReportUnreadable` | 无 (环境故障, 与 `on_conflict` 无关) |
| `Absent` | — | `Create` | 创建缺失父目录, 建立链接 |
| `LinkedCorrect` | — | `Noop` | 无 |
| `LinkedWrong` | `skip` | `RefuseConflict` | 无 |
| `LinkedWrong` | `replace_and_backup` | `ReplaceAndBackup` | 备份**该链接本身** (不跟随), 建立链接 |
| `ForeignFile` | `skip` | `RefuseConflict` | 无 |
| `ForeignFile` | `replace_and_backup` | `ReplaceAndBackup` | 备份该文件, 建立链接 |
| `ForeignDir` | `skip` | `RefuseConflict` | 无 |
| `ForeignDir` | `replace_and_backup` | `ReplaceAndBackup` | 备份该目录 (递归), 建立链接 |
| `ForeignLink` | `skip` | `RefuseConflict` | 无 |
| `ForeignLink` | `replace_and_backup` | `ReplaceAndBackup` | 备份该链接本身 (不跟随), 建立链接 |

### 3.2a 目标谓词的求值基准 (退出码条件 1 的输入)

`contracts/cli.md` 的四条目标谓词都以"每个条目的目标路径"为量词, 而谓词的输入是**判定结果**, 不是文件系统实况. 二者在 `Absent` 与 `SourceMissing` 上会给出相反答案, 因此必须钉死:

- `Absent` **计数**为"该目标路径尚未成为正确链接" -> 使 `apply` 的谓词为假 (退 1), 使 `undo` 的谓词为真 (该路径上没有本工具的链接). 它对两条命令的作用相反, 这不是矛盾: 谓词问的是不同的期望状态.
- `SourceMissing` **不计数**: 一个没有源的条目无法"成为正确链接" (该目标不可达成), 但它的残留待办**已由退出码条件 2 表达** (`missing` 计入"失败"列, 使四条命令一律退 1). 若谓词也计数, 条件 1 与条件 2 会在同一批条目上重复生效, 且会使 `undo` 在一份只含 `SourceMissing` 的清单上恒退 1 (与"条件 2 独立于条件 1"在契约中作为判别点出现相冲突).
- `Unreadable` 同理**不计数** (环境故障, 不是"目标可达成但未达成").
- `LinkedCorrect` 使 `apply` 的谓词为真, 使 `undo` 的谓词为假.

**谓词只依赖 `Current`, 不需要 `Action`**: 由上表, "该条目是否还需动作"完全由 `Current` 决定 (`Action` 是 `Current` 与 `on_conflict` 的函数, 不含额外信息). `tasks.md` 中"谓词 = 每个 `Action` 均为 `Noop`"是对**可执行条目**的等价说法, 它以"排除 `SourceMissing` / `Unreadable`"为前提; 三处表述以本表为准.

### 3.3 命令与状态的消费关系 (FR-017 的结构保证)

| 命令 | 使用的字段 | 是否写文件系统 |
|------|-----------|----------------|
| `preview` | 全部 (`Current` + `Action`) | 否 |
| `apply` | 全部, 执行 `Action` | 是 |
| `status` | 仅 `Current` | 否 |
| `undo` | `Current`, 并只在 `LinkedCorrect` / `LinkedWrong` 时撤销 | 是 |

四个命令消费**同一个** `classify` 返回值, 因此同一状态下结论一致是由数据流保证的, 而非靠三处逻辑各自对齐.`undo` 需要判断"链接是否落在仓库内"时**只读 `Current` 即可** -- 因为 `LinkedWrong` 的定义本身已包含"`L` 落在 `R` 之内", `ForeignLink` 已包含"`L` 落在 `R` 之外". 归属判定被吸收进 `Current` 的取值, 不再需要第二次 `readlink`.

`undo` 的 token 不按 3.2 的 `Action` 导出, 而有自己的分支: `LinkedCorrect` / `LinkedWrong` 按同目录有无备份分别为 `restore` / `undo`, `ForeignLink` / `ForeignFile` / `ForeignDir` 为 `skip`, **`Absent` 为 `ok`** (该路径本就没有本工具创建的链接, 因而"已是最新"), `SourceMissing` 为 `missing`, `Unreadable` 为 `fail`. 其中 `Absent -> ok` 是撤销幂等的关键: 它使"已撤销干净的清单上再次运行 `undo`"落入"已是最新"列并退 0; 若误归为 `skip`, 第二次 `undo` 将退 1. 完整的 token 表以 `contracts/cli.md` 的"状态 token 表"与"`undo` 分支"为准, 本模型不另立第二处来源.

### 3.4 状态迁移 (以单条目为视角)

```text
                 +--------------------------------------------+
                 |                                            |
   [Absent] --apply/Create--> [LinkedCorrect]                |
      ^                            |                         |
      |                            | apply 后用户手工改坏了   |
      |                            v                         |
      |                     [ForeignFile] <-/ForeignDir/     |
      |                            |        ForeignLink       |
      |                            |                         |
      |   undo (移除链接,           | apply/ReplaceAndBackup |
      |   若有备份则恢复)           v                         |
      +---------------------- [LinkedCorrect] ---------------+
                               (备份留存于同目录)

   [SourceMissing] 是终态: 在源条目被补回仓库之前, 任何 apply/undo 都不改变它.
```

撤销的语义边界 (FR-009 / FR-010): `undo` 只在 `Current` 属于 `LinkedCorrect` / `LinkedWrong` 时才移除链接; 其余情况 (含 `ForeignLink`) 一律跳过并报告原因, 绝不删除.这正是"绝不触碰非本工具创建的路径"由 `Current` 的类型直接保证 -- 外部链接落在 `ForeignLink`, 而 `undo` 的分支不包含它.移除链接后, 若同目录存在 `<原名>.dotlink-backup.*`, 恢复最新一个.

## 4. Backup (备份)

不持久化索引 —— 它是"文件系统上的命名约定", 而不是需要维护的数据结构.

| 属性 | 值 |
|------|-----|
| 位置 | 被覆盖路径的同一目录 |
| 名称 | `<原名>.dotlink-backup.<YYYYMMDDThhmmss>`, 同名已存在时追加序号 `<原名>.dotlink-backup.<YYYYMMDDThhmmss>.<n>` (n 从 2 起) |
| 时间戳 | 本地时区, 秒级 |
| 内容 | 原对象的一份副本.原对象是文件/目录则递归复制; 原对象是符号链接则复制**链接本身** (不跟随) |
| 查找 | 撤销时取同目录下名称以 `<原名>.dotlink-backup.` 开头者中字典序最大 (等价于时间最新) 的一个 |

**完整性 (写入顺序)**: 递归复制一个目录可能在中途被中断, 而"字典序最大"这一查找规则无法分辨完整与不完整的备份. 因此备份的写入必须是**两步**: 先复制到临时名 `<原名>.dotlink-backup.<YYYYMMDDThhmmss>.partial`, 全部复制成功后再原子改名为最终名. 最终改名成功即视为该备份"已完整". 与 R8 的"符号链接创建本身即原子"是同一原则: 不向外暴露半成品状态.

**查找规则因此收窄**: `find_latest_backup` **只接受已完整命名的备份** (名称不含 `.partial` 后缀). 中断残留的 `.partial` 文件既不参与"取最新", 也不被 `undo` 消费; 它们与原备份一样留在磁盘上, 由用户自行清理. 该残留路径计入 `research.md` R4 的"已知限制".

**先复制后删除的硬顺序**: 备份的**全部**内容在磁盘上落定并被改名之后, 才允许删除/替换原对象. 递归复制一个**目录**可能在中途失败 (权限, 磁盘满, 中断), 而原对象是唯一的副本; 若先删除再复制, 一次中途失败就是不可恢复的数据丢失, 直接违反 SC-004 与 US3 的立项目标. 因此顺序严格为: 复制到 `.partial` -> 复制成功 -> 改名为最终名 -> 删除原对象 -> 建立链接. 任一步在此之前失败, 原对象必须原样保留, 该条目报 `fail` 并说明原因 (对应 `tasks.md` 的 T025).

**唯一性 (命名消歧)**: 构造备份名时若目标名已被占用, 必须追加序号消歧, 绝不覆盖既有备份. 这覆盖两类情形:

1. **同一秒内的两次替换**: 秒级时间戳使"apply -> undo -> apply"或"目录条目被 replace 后紧接另一路径 replace"可能落在同一秒内, 二者本会算出同一路径名.
2. **并发覆盖**: 同一时刻对同一路径的并发覆盖 (见 R8).

消歧后所有备份文件都保留, 命名中的时间戳 + 序号使"字典序最大"仍等价于"最新", 撤销取该最新者. 这一规则使 R4 的"更早的备份仍在磁盘上但不被自动使用"从"可能被覆盖丢失"变为"确定留存".

## 5. Report (报告, 非持久化)

行格式 (`<序号>/<总数> <token> <用户书写的 target> <说明>`) 与末尾汇总的**唯一权威定义在 `contracts/cli.md` 的"输出契约"**, 本节不另立第二处字段列表. 列出如下仅为便于对照:

```text
1/4 create   ~/.bashrc           未部署 -> 已创建链接
4/4 missing  ~/.config/nvim      源缺失 (仓库中不存在: nvim)
```

注意**不设"源条目"列**: 一行已经承载了序号, token, 用户书写的 target 与说明, 再加一列源条目会把行拉长到需要折行, 而源条目在 `missing` 一类说明中本就以文字给出. 也**不设"动作措辞"列**: `status` 只渲染 `Current` 不渲染 `Action`, `undo` 走自己的分支也不按 `Action` 导出 token, 因此没有一份四命令共有的"动作"列.

末尾汇总的四项计数**互斥**且相加恒等于总条目数: 成功 / 已是最新 / 未处理 / 失败 (token 归类见 `contracts/cli.md` 的"汇总列 / token"对照表). 第三列的列名是 token 分桶名而非动作陈述 -- 它同时收容"有意不处理"的 `conflict` / `skip` 与"没有动作可执行"的 `foreign` / `absent` / `wrong`, 后三个出现在只读的 `status` 上.

**退出码** (对外契约, 见 `contracts/cli.md`): 0 = 该命令的目标谓词成立且无遗留待办; 1 = 存在未达成目标的条目, 或有被跳过/被拒绝/失败/源缺失的条目; 2 = 清单校验失败 **或调用方式错误**, 未做任何改动; 3 = 平台不受支持.

完整的两个条件与各命令的目标谓词见 `contracts/cli.md` 的"退出码"小节; 本节不另立数字表, 以免出现第二个可与之矛盾的来源.
