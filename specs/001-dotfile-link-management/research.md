# Phase 0 Research: 声明式 dotfile 软链接管理

本文件解决 `plan.md` 的 Technical Context 中所有需要裁决的事项, 以及规格中三个高风险未决点 (链接归属判定,冲突默认策略,清单格式).每项给出结论,理由与被否决的替代方案.

---

## R1. 清单文件格式

**Decision**: TOML, 文件名固定为**当前工作目录**下的 `dotlink.toml`; 不向上搜索父目录, 该文件所在目录即仓库根目录.

**Rationale**:
- 需要条目级开关 (如"允许对这条做备份替换"), TOML 的嵌套表天然表达数组内每个元素带字段, 无需缩进敏感语法.
- 用户在 `~/.claude/CLAUDE.md` 中的规则要求所有文本使用半角标点; TOML 的字符串与键名不受正则化影响, 不引入全角标点风险.
- 与 Rust 生态集成成本最低 (`toml` + `serde`), 且 diff 表现优于 JSON.

**Alternatives considered**:
- *YAML*: 表达力足够, 但对缩进敏感, 且解析实现体积与已知陷阱 (如 `no` 被解析为布尔,挪威问题) 高于收益.
- *JSON*: 不支持注释与尾随逗号, 作为需要手工编辑的配置文件体验明显更差; 也无法表达"默认值 + 覆盖"的可读结构.
- *自定义 DSL / S 表达式*: 表达力过剩, 需要自写解析器与错误报告, 违背"不预建扩展点".

**Consequence**: 清单缺失,不可读,TOM 语法非法均属 FR-013 的整体拒绝场景.

## R2. 链接归属判定 (规格中风险最高的假设)

**Decision**: 路径 P 上的链接被视为"由 dotlink 创建", 当且仅当同时满足:
1. `lstat(P)` 显示 P 是符号链接;
2. P 的链接文本解析为绝对路径后, 经**非严格 realpath** (`os::normalize`, 见下方"Decision") 规范化后的结果落在同样规范化的仓库根目录之内 (即等于仓库根, 或是其子孙).

任一条不满足即视为"非本工具创建", 因此 `undo` 会跳过它 (FR-010), 部署时将其视为冲突 (FR-007).

**Rationale**: 该规则完全由文件系统实况推导, 不需要状态文件 (FR-012), 因此不存在"状态文件与实况脱节"这一类失效模式 —— 用户手工删掉链接,移动仓库,或换机器重新 clone 后, 判定依然正确.

**Alternatives considered**:
- *状态数据库 (如 `~/.local/state/dotlink/links.json`)*: 可提供精确归属, 但引入第二个事实来源, 会出现与文件系统不一致的态; 用户手工清理后状态文件变成需要维护的垃圾.与 FR-012 直接冲突, 已由规格排除.
- *命名约定 (链接文本带 `dotlink:` 前缀)*: 归属判定简单, 但会污染链接目标 (用户 `cat` 一个链接会看到伪路径), 且破坏"链接即真实路径"的直觉; 部分工具对链接文本做前缀匹配也会受影响.
- *仅按 `readlink` 的**字面**前缀比较 (不做规范化)*: 已被实测否决, 见下方"实测发现".

**实测发现 (关键的实现陷阱)**: 本机验证:
```
$ ln -sfn /tmp/dl_probe/repo/nvim /tmp/dl_probe/home/.config/nvim
$ python3 -c "print(os.path.realpath('/tmp/dl_probe/repo/nvim'))"
/private/tmp/dl_probe/repo/nvim
```
(该 `ln` 必须是 `-f`/`-n` 形态: 若目标路径已存在, 不带 `-f` 的 `ln -s` 会以 `File exists` 失败而不改动链接, 实测确认.)
macOS 上 `/tmp` 是指向 `/private/tmp` 的符号链接.若只做字面前缀比较, 或只对其中一侧做规范化, 归属判定就会在 (a) macOS 的 `/tmp` 与 `/var` 下,(b) 仓库路径中含 `..` 时,(c) 用户主目录本身是符号链接时 全部失效 -- 后两者在真实 dotfile 用法中很常见.因此 `classify` 的实现必须对**两侧**都做规范化后再比较.这也意味着本功能的测试夹具自身就落在 macOS 的规范化路径差异之下, 测试必须覆盖这一情形而非回避它.

**补充陷阱: 规范化必须是非严格的 (悬空链接)**. 本机实测确认 Rust 的 `Path::canonicalize` 与 Python 的 `os.path.realpath(strict=True)` 行为一致: 当路径的**末端或其任一段不存在**时返回 `Err` / 抛 `FileNotFoundError`:

```
链接 /tmp/dl_probe/home/dangling -> /tmp/dl_probe/repo/gone (gone 不存在)
realpath strict  -> FileNotFoundError
realpath 非严格  -> /private/tmp/dl_probe/repo/gone     # 仍能给出规范化结果
```

这不只是理论问题: 悬空链接在 dotfile 场景里很常见 (用户在仓库里重命名/删除了一个源文件, 而旧链接还留在主目录). 若判定用 `canonicalize`, 一个指向仓库内但已失效的链接会因为 `Err` 而被降级处理, 在"规范化失败即视为落在仓库外"的实现下会被误判为 `ForeignLink`, 于是 `undo` 拒绝清理 dotlink 自己创建的悬空链接 -- 一个只有用户手工 `rm` 才能收拾的残留.

**Decision (R2 的完整形态)**: 归属判定与路径相等判定统一使用一个**自实现的非严格 realpath** `os::normalize`, 在 `classify` 与 `undo` 中自始至终使用同一个函数. 它的语义分两段:

1. **已存在的路径段解析符号链接**: 自根向下逐段走, 若某段 (即"已解析前缀 + 该段") 是符号链接, 则读取其文本并继续解析, 直到得到一个非链接的已存在路径段. 这正是"实测发现"中 macOS `/tmp` -> `/private/tmp`,`/var` -> `/private/var` 所要求的 -- 只有解析符号链接才能让别名形态与物理形态落回同一个字符串.
2. **不存在的尾段按词法规整**: 一旦某段不存在 (即 `lstat` 返回 `NotFound`), 该段及其后所有段不再访问文件系统, 只做词法处理 (逐段消除 `.` 与 `..`). 这满足"补充陷阱"的硬性要求: 悬空链接仍能被规范化, 不因 `Err` 而被误判为落在仓库外.

因此 macOS 路径别名与悬空链接这两类情形由**同一个函数的两段语义**覆盖, 不需要两套分支. 绝对路径的根前缀被保留, `..` 上溯到根后不再回退; 相对路径开头, 已到路径起点时的 `..` 必须保留而不被抵消 (`../../a` 不得退化为 `a`). 符号链接环由深度上限截断, 达到上限后退化为词法处理, 不得无限递归.

**这两个要求为何不能只满足其一**: 若 `os::normalize` 只做词法规整 (不解析符号链接), 则 macOS `/tmp` 别名形态的链接与物理形态的仓库根永远不会判等 -- 一条由本工具创建的链接会被误判为 `ForeignLink`, `undo` 因此拒绝清理自己的产物 (这正是 `tests/status.rs` 中 `a_link_written_with_the_tmp_alias_is_still_ok` 所锁定的缺陷). 反之若改用 `Path::canonicalize` (严格 realpath), 悬空链接会因 `Err` 而无法归类. 二者必须同时成立.

**该函数有且仅有三个调用点**, 且三者必须共用它 (而非两处用它, 一处用 `Path::canonicalize` 或原始拼接):

1. `L` -- 目标路径上的链接文本解析为绝对路径后 (`classify`);
2. `R` -- 仓库根 (`link_is_inside_repo` 与 `classify`);
3. `S` -- 仓库根与 `source` 拼出的 `source_path` (`entry.rs` 产出时即规范化).

第 3 点是容易漏掉的一处: 若 `S` 保留字面拼接结果而 `L` 已被规范化, `L == S` 的比较就落在两套不同的路径语义上. 因此 `source_path` 必须在解析阶段 (而不是在 `classify` 内部) 就过一次 `normalize`, 使 `R` / `S` / `L` 三者同源 (`data-model.md` 2 节的解析产物表).

## R3. 冲突的默认策略与显式覆盖的粒度

**Decision**: 默认拒绝覆盖 (FR-007).显式覆盖以**条目级**开关表达, 位于清单每个条目内; 不提供命令行级全局覆盖开关 (FR-008 明确禁止).取值名为 `replace_and_backup` 而非 `backup`, 使清单字面即可读出该条目的完整行为: 先替换 (以备份方式), 再建立链接.

```toml
[[entry]]
source = "bash/bashrc"
target = "~/.bashrc"
on_conflict = "replace_and_backup"     # 默认 "skip"; 另一合法取值 "replace_and_backup"
```

**Rationale**:
- 粒度选择是实质取舍: 条目级开关一次配置长期生效, 每次部署行为可预测且可版本化 (写在仓库里, 换机器后行为一致); 命令行全局开关则每次执行都可能不同, 容易在自动化脚本里被复制成危险默认值.
- 一个全局 `--force` 会让新机器上第一次部署把整批冲突文件静默备份替换 —— 正是规格 US3 要避免的失败模式.
- 冲突的默认策略由规格确定为"拒绝"; 此处只决定"许可"如何表达, 属于设计层裁决.

**Alternatives considered**:
- *命令行 `--on-conflict=backup` 全局开关*: 使用更顺手, 但把"是否覆盖"从声明式配置降级为每次调用的瞬时决定, 与"声明式清单是唯一事实来源"矛盾.
- *两者都提供*: 两个来源需要定义优先级, 且允许"配置说 skip 但命令行强制 backup", 会让清单不再是唯一事实来源.违背"不为减少接口而合并无关职责"的反面 —— 这里是"不必要的第二个入口".
- *交互式询问*: 与"无交互提示,可脚本化"约束冲突, 已由规格排除.

## R4. 备份的位置与命名

**Decision**: 备份存放在**被覆盖路径所在目录**中, 命名为 `<原名>.dotlink-backup.<YYYYMMDDThhmmss>`; 时间戳取本地时区的秒级精度.撤销时恢复"该路径上文件名前缀匹配 `<原名>.dotlink-backup.` 的**最新**一个".

**Rationale**: 用户在出错后最容易想到的查找位置就是"原来那个文件的旁边"; 集中备份目录需要用户知道并记住另一个路径.时间戳提供可排序性, 使"取最新"有确定答案; 同一时间戳下的重名由追加序号消歧 (见下"唯一性"), 因此任何一次覆盖都不会使既有备份消失.

**Alternatives considered**:
- *系统临时目录 / 统一备份目录*: 会被系统清理, 或需要用户记住额外路径, 削弱"可找回"这一唯一目的.
- *固定后缀 `.bak` (无时间戳)*: 第二次覆盖会丢掉第一次的备份, 且无法回答"我上一次的原始文件在哪".
- *版本化备份目录 + 索引*: 表达力过剩, 引入需维护的状态; 与"不做超出一个条目已知需求的设计"冲突.

**唯一性 (命名消歧, 首版即解决)**: 若构造出的备份名在磁盘上已存在, 追加序号 `<原名>.dotlink-backup.<YYYYMMDDThhmmss>.<n>` (n 从 2 起) 直到得到未被占用的名字, 绝不覆盖既有备份. 这同时覆盖"同一秒内对同一路径的两次替换"与"跨进程并发覆盖同一路径". 消歧后 `(时间戳, 序号数值)` 最大者即"最新", 撤销取该最新者 (不按整名字典序 -- 序号 `10` 的字典序小于 `9`).

**顺序与数据安全**: 备份必须**完整落定之后**才删除原对象 (`data-model.md` 第 4 节的"先复制后删除的硬顺序"). 这不是风格问题 -- 递归复制目录可能中途失败, 而原对象是唯一副本; 顺序颠倒会让一次失败变成不可恢复的数据丢失, 使 SC-004 的"100% 不静默丢弃"不成立.

**已知限制 (明确记录, 不在首版解决)**: 同一路径被覆盖两次后, 撤销只会恢复最近一次备份, 更早的备份仍留在磁盘上但不被自动使用.同理, 复制中途被中断留下的 `<原名>.dotlink-backup.<ts>.partial` 既不被"取最新"接受, 也不被撤销消费 (见 `data-model.md` 第 4 节的完整性规则), 永久留存至用户自行清理.本工具不提供备份垃圾回收.

## R5. 目标路径的解析规则

**Decision**: 目标路径按下述顺序解析:
1. 以 `~` 开头 → 展开为当前用户主目录; `~/x` 展开为主目录下 `x`.
2. 不含 `~` 且为绝对路径 → 原样使用.
3. 不含 `~` 且为相对路径 → 相对于**清单文件所在目录** (即仓库根) 解析.

源条目路径始终相对于**清单文件所在目录**解析.仓库根目录由清单文件位置唯一确定.

**Rationale**: 相对目标路径相对仓库根解析, 使整份清单具备可移植性 (换机器,换用户后无需改动), 这是 dotfile 工具的核心诉求.

**完整的配置面只有一个位置** (与本文件 R5 及规格 FR-015 一致): 命令必须在含 `dotlink.toml` 的目录下执行; 既没有 `--repo` / `--manifest`, 也没有对应的环境变量.用户需要建立的模型是"我 cd 到清单所在目录, 然后运行命令", 其中不存在第二个可与之矛盾的信息来源, 因此也不存在"清单在这里,仓库根在那里"这类需要用户自行协调的不一致状态.代价是拒绝"在仓库子目录里直接运行"的便利性 —— 这一条由规格显式选择, 属于有意为之而非遗漏.

**Alternatives considered**:
- *相对路径相对于当前工作目录*: 结果取决于调用者在哪个目录执行命令, 同一份清单在不同目录下行为不同, 不可接受.
- *仅允许绝对目标路径*: 破坏可移植性, 与集中管理的初衷冲突.

**边界确认**: 主目录无法确定时 (无 `HOME` 且无法从别处推导) 属于 FR-013 的整体拒绝场景, 不做任何改动.

**边界确认 (当前工作目录不可用)**: 清单路径由"当前工作目录 + `dotlink.toml`"拼出, 因此取当前工作目录是解析的第一步. 该目录已被删除时取值失败 (本机实测: Rust 的 `std::env::current_dir()` 与 Python 的 `os.getcwd()` 此时都会失败), 此时无法构造清单路径, 更无法读取. 处置与"清单不存在"相同 (退出码 2, 零改动), 但说明必须不同 (FR-015): 报"找不到 `dotlink.toml`"会让用户去检查目录而看不到真正的原因.

## R6. 平台门禁的实现位置 (FR-019)

**Decision**: 平台检查是 `run()` 的**第一步**, 早于参数解析,早于清单读取.在不支持的平台上, 进程以退出码 3 结束, 向标准错误输出一行说明, 不产生任何标准输出, 不触碰文件系统.同时, 非 unix 平台提供符号链接操作的**可编译空实现**, 使二进制在 Windows 上仍能构建成功.

**Rationale**:
- 检查放在最前, 才能满足规格新增的边界情况: "在读取清单与做任何判定之前即结束, 不产生部分输出误导用户".
- 若改为 `#[cfg(not(unix))] compile_error!`, 则 Windows 上根本无法得到二进制, 用户看到的是编译错误而非可读提示, 不满足"明确拒绝运行"的要求.因此需要"可编译 + 运行时拒绝"的组合.
- 退出码 3 与校验错误 (2),条目失败 (1) 区分开, 使脚本能辨别"环境不支持"与"清单/操作有问题".

**Alternatives considered**:
- *编译期拒绝 (`compile_error!`)*: 简单且编译产物不会误用, 但用户无法得到可读提示, 且无法在 CI 中对 Windows 目标做构建验证.
- *运行时静默降级为复制文件*: 与"无降级路径"的规格决策直接冲突, 且复制语义与链接语义在"改仓库即生效"上根本不同.

## R7. 报告的渲染与"结论一致"的保证方式 (FR-016 / FR-017)

**Decision**: `classify` 是唯一的判定入口, 签名为 `classify(&Manifest) -> Vec<EntryState>`; 每个 `EntryState` 同时携带"现状"与"应执行的动作"两个字段.`preview` 打印动作而不执行, `apply` 执行动作, `status` 只打印现状, `undo` 消费同一判定后走撤销分支.报告渲染由单一的 `render` 模块负责.

**Rationale**: FR-017 要求同一状态下四条路径结论一致.若靠"四处各写一遍判定逻辑再靠测试对齐", 一致性只能靠纪律维持; 改为让四者消费同一个返回值, 则一致性由**类型与数据流**保证, 不可能出现分歧.这同时也是本设计中最重要的一处"深模块": 调用者不需要知道"什么算冲突""什么叫已是最新", 只需要读结论.

**Alternatives considered**:
- *每个命令自建判定*: 代码更"直白", 但立刻违反 FR-017, 且后续任何规则调整都需同步三处.
- *trait 化的 Action 策略对象*: 为四种固定动作引入动态分派, 属于为模式而增加层次; 用 `enum Action` 直接匹配即可.

## R8. 并发执行的策略

**Decision**: 首版不引入锁.并发部署的后果被限制为"不静默产生错误结果": 符号链接的创建与替换在单个条目层面是原子的 (要么旧状态要么新状态, 不存在半成品链接), 两个进程可能在同一条目上重复备份, 但不会产生指向错误位置的链接.

**Rationale**: 规格将并发列为边界情况但未要求串行化保证; dotfile 部署是低频,用户主动触发,单机操作, 引入文件锁会带来锁文件残留,死锁与跨主机文件系统语义 (NFS) 等真实复杂度, 而收益近乎为零.

**Alternatives considered**:
- *`~/.cache/dotlink.lock` 文件锁*: 复杂度与收益不成比例; 且锁文件本身会成为新的"需要清理的状态".
- *先写临时名再 `rename` 的占位方案*: 对符号链接而言与直接创建等价 (创建本身即原子), 属于多余步骤.

**记录为已知限制**: 首版不保证并发调用的串行化, 并发场景下可能出现重复备份文件.此限制明确写入交接说明, 不隐式掩盖.

## R9. 是否需要 `status --quiet` / 机器可读输出

**Decision**: 不实现.所有命令仅提供人类可读输出.

**Rationale**: `status` 的用途已被退出码很好覆盖 (全部符合 → 0; 存在偏离 → 非 0), 脚本可用退出码判断, 无需解析文本.规格 SC-007 只要求"仅凭命令行输出即可判断每个条目的结果与下一步动作", 未要求机器可读格式.为一个未确认的需求引入输出格式开关, 属于为假想需求预建扩展点.

**Alternatives considered**: *`--json` 输出*: 待出现真实的脚本化消费需求时再加, 届时是加法而非破坏性变更.

## R10. 只读命令的退出码是否表达"有待办"

**Decision**: 表达.`preview` 与 `status` 在存在待执行动作或偏离时退出 1, 完全符合时退出 0.

**通用判据 (适用于四条命令)**: 退出 0 当且仅当**该命令自身的期望状态已达成, 且没有遗留待办**. 判据由两个条件合成, 而不是"执行了几个动作". 两个条件的完整表述, 各命令的目标谓词表, 以及谓词的求值基准 (`SourceMissing` / `Unreadable` 不计数) 一律以 `contracts/cli.md` 的"退出码"小节与 `data-model.md` 3.2a 为准 -- 本节不重复其内容, 以免出现第二个可与之矛盾的来源.

**本节只记录两处裁决理由** (其余属契约的执行细节):

- **为何条件是"目标"而非"动作数"**: 只有命令专属的目标谓词能同时给出三个正确答案 -- `apply` 第二次运行 (全部 `ok`) 退 0, `undo` 在撤销后目标为空的清单上退 0 (幂等), 而 `preview` 在未部署的清单上退 1. 若统一成"有没有做动作"或"有没有条目失败", 这三者无法同时成立.
- **一处必须显式记录的非对称**: `undo` 的目标谓词与 `apply` **刻意相反**, 且 `undo` 的谓词在动手**之前**求值. 因此"二者退出码恒等"不成立, 且不得为了看起来一致而改动其中一方.

**`preview` 与 `apply` 的关系需要精确表述**: 二者共用同一个目标谓词, 差别只在求值时刻 (`preview` 在动手前, `apply` 在动手后). 不得为了让二者一致而在 `preview` 中产生副作用 (`preview` 的只读性是 SC-006 的前提).

**Rationale**: 这让只读命令可直接用作前置检查, 无需解析文本:

```sh
dotlink status  || echo "配置有偏离, 需要处理"
dotlink preview && echo "已完全符合期望"
```

该约定与成熟工具的既有做法一致 (`git diff --exit-code` 在有差异时退出 1, `terraform plan -detailed-exitcode` 在有变更时给出非零详细码), 因此不会让用户意外.

**Alternatives considered**:
- *只读命令一律退出 0, 仅错误时非 0*: 更保守, 但会迫使脚本解析文本才能判断偏离; 而 R9 决定不提供机器可读输出, 两个决策叠加后脚本将无法可靠判断, 形成能力缺口.
- *沿用 `terraform` 的详细码 (0/2 表示变更)*: 与本工具已有的退出码 2 (清单校验失败) 和 3 (平台不支持) 冲突, 无法容纳.

**代价与缓解**: 在 `set -e` 的脚本中裸调 `dotlink preview` 会中断执行.这一点必须在 `--help` 与 README 中显式说明; 上面两条用法示例即推荐写法.
