# 契约: 命令行接口

**契约类型**: 面向用户与脚本的公开接口.退出码与输出行的关键字段是脚本可依赖的部分; 行内其余文字措辞可调整.

---

## 命令面

```text
dotlink <COMMAND>

Commands:
  preview   只读: 报告每个条目将会发生什么, 不修改文件系统
  apply     执行: 按清单建立链接 (必要时先备份)
  status    只读: 报告清单与实际状态的不一致
  undo      撤销: 移除本工具创建的链接, 并恢复备份

Options:
  -h, --help
  -V, --version
```

`-h` / `-V` 与"子命令缺失或拼错"均由 `clap` 直接处理, 不经过 `run()` 的退出码计算: 前两者向标准输出打印帮助/版本并退 0 (属正常路径, 不在下面的四类结局之内), 后者向标准错误打印用法说明并退 2 -- 见下方"调用方式错误".

**已刻意不提供**:
- `--repo` / `--manifest` 及其对应的环境变量: 仓库根与清单位置由当前工作目录下的 `./dotlink.toml` 唯一确定 (见 `contracts/manifest.md`).配置面只有这一个位置, 没有任何可能与之矛盾的第二个来源.
- `--force` 等全局覆盖开关: 覆盖许可是**条目级**声明 (`on_conflict = "replace_and_backup"`), 使行为可版本化,换机器后一致 (见 `research.md` R3).
- `--json` 等机器可读输出: 脚本可用退出码判断, 未出现真实需求前不加 (见 `research.md` R9).
- `--home`: 主目录取自 `HOME` 环境变量.

从当前工作目录读取 `dotlink.toml`; **不向上搜索父目录**.在仓库子目录中执行视为清单不存在 (退出码 2).

## 平台门禁

在任何参数解析与清单读取**之前**检查平台.不受支持时: 标准错误输出一行说明, 标准输出为空, 退出码 3, 不触碰文件系统.

```text
dotlink: 不支持当前平台 (仅支持 macOS 与 Linux)
```

## 退出码

统一语义: **退出 0 当且仅当"该命令所关心的期望状态已达成, 且没有遗留待办"**.

该语义由两个条件合成, 二者必须**同时成立**才退出 0:

1. **目标谓词成立**: 该命令自身的期望状态已达成 (见下表).
2. **无遗留待办**: 全部条目都落在输出汇总的"成功"或"已是最新"两列. 换言之, 不存在任何被跳过,被拒绝,失败或源缺失的条目 (token 归类见下方"输出契约").

条件 2 独立于条件 1, 它保证"跳过"这类无法通过动作消除的条目总能得到可区分的非成功状态 -- 例如 `undo` 在一个被真实目录占用的路径上无从下手, 目标谓词虽已成立, 但仍必须退 1 并报告 `skip` (见 `quickstart.md` 场景 6). 同理, `SourceMissing` 恒使退出码为 1, 与它被计入"失败"列一致.

退出码由**该命令自身的目标是否已达成**导出, 而不是由"执行了几个动作"导出. 四类结局如下 (只读与写入命令共用同一套数字):

| 码 | 含义 (适用于全部四条命令) |
|----|---------------------------|
| 0 | 该命令的目标已完全达成, 且无遗留待办 |
| 1 | 存在未达成目标的条目, 或有被跳过/被拒绝/失败/源缺失的条目 |
| 2 | 清单校验失败 **或调用方式错误** (未做任何改动) |
| 3 | 平台不受支持 |

### 调用方式错误 (与退出码 2 共用码值)

子命令缺失, 子命令拼错 (如 `dotlink statu`) 与未知选项不属于上面四类结局, 但它们由 `clap` 的参数解析直接拒绝: 在**读取清单之前**结束, 向标准错误打印用法说明, 退出码 **2**, 不修改文件系统. 这与"清单校验失败"共用码值, 是所选工具链 (`clap` 对 stderr 类错误固定退 2, 不提供自定义出口) 的直接结果; 二者的**可区分性**由输出承担, 不由码值承担:

| 结局 | 标准错误的内容 |
|------|----------------|
| 调用方式错误 | 用法说明 + `unrecognized subcommand` 之类的解析错误, 附正确子命令列表 |
| 清单校验失败 | `dotlink: 无法读取清单 ./dotlink.toml: ...` 之类的单行说明 |

因此 `contracts/cli.md` 对 FR-020 的"四类结局"保持 0/1/2/3 的映射不变, 调用方式错误是**第五类结局**, 其可区分方式为"标准错误是否为用法说明". 各子命令的 `long_about` 必须写明这一点 (见 `tasks.md` 的 T041), 以满足 SC-009 的"仅凭命令行输出即可判断".

各命令的"目标谓词" (条件 1) 按下表确定. 这是唯一允许的解读, 实现不得另立标准:

| 命令 | 目标谓词 (条件 1 的充要条件) |
|------|------------------------------|
| `apply` | 每个条目的目标路径都已成为指向其源条目的正确链接 |
| `undo` | 每个条目的目标路径上都**不存在**由本工具创建的链接 (备份已恢复或不适用) |
| `preview` | 没有任何条目需要执行动作. 等价于"每个条目的 `Action` 均为 `Noop`" |
| `status` | 清单与实际状态完全一致: 没有任何偏离 |

`undo` / `restore` 的 token **不由 `Action` 导出**: `Action` 枚举 (见 `data-model.md` 3.2) 只覆盖"建立链接"这一侧的动作, 不含任何移除类取值; `undo` 走的是自己的分支 (见下方"`undo` 分支"), token 由 `(Current, 同目录是否有备份)` 决定, 与 `Action` 无关.

实现时必须先算出全部条目的结果, 再同时套用两个条件: 由"逐条结果 + 该命令的目标谓词"导出退出码的单一函数, 四个命令共用, 不得各写一份.

`preview` 的条件 1 与条件 2 在有实际待办时重合 (那些条目必然落在"未处理"列), 因此二者的差别只在"目标本已达成但有条目无法通过动作消除"这一类 -- 这类情形由条件 2 单独拦下 (`SourceMissing` 在四条命令下一律退 1), 见 `quickstart.md` 场景 14.

**为何判据是"目标"而非"动作数"**: `apply` 的第二次运行 (全部 `ok`) 必须退出 0, 尽管它与第一次相比少做了动作; `undo` 在一条撤销后目标路径为空的清单上必须退出 0 (幂等), 尽管它一个动作也没做; 而 `preview` 在未部署的清单上必须退出 1, 尽管它同样一个动作也没做. 三例合起来说明: 只有命令专属的目标谓词能同时给出这三个正确答案.

**只读命令与写入命令的对偶**: `preview` 与 `apply` 使用**同一个**目标谓词 (是否已完全符合期望), 但求值时刻不同 -- `preview` 在动手**之前**求值, `apply` 在动手**之后**求值. 因此在一份尚未部署的清单上, `preview` 退 1 ("有活要干"), 而 `apply` 把活干完后退 0; 二者只有在清单本已完全符合期望时才同为 0. 不得把它读成"二者应恒等", 更不得为了让退出码一致而在 `preview` 中执行动作.

**`undo` 与它们刻意相反**: 一份刚部署好的清单上 `apply` 退 0, `undo` 退 1 (有链接待撤). 这是预期行为, 不是不一致. 它同样不能被实现成"按动作数计": 撤销后目标为空 (无备份可恢复, 或恢复后目标为空) 时再运行必须回到 0.

**`undo` 的谓词在动手之前求值**: 这一点必须明说, 否则会被读成"撤销后再看还剩多少链接" (那样任何情况都恒为 0). `undo` 的谓词问的是"**本次要撤销的清单**上是否还有本工具创建的链接", 在动作**之前**取一次值. 因此刚部署好的清单上该谓词为假 -> 退 1; 对一份本就没有本工具链接的清单 (含撤销后目标为空的再次运行) 该谓词为真; 谓词为真时若条件 2 也通过 (无 `skip` / `missing` 等残留) 则退 0. 同时, 撤销过程中新暴露出的 `skip` / `missing` 等条目仍会通过条件 2 让退出码为 1, 这正是"条件 2 独立于条件 1"的作用.

由此 `preview` 在一个尚未部署的仓库上退出 1, 语义是"有活要干", 可用作部署前置检查:

```sh
dotlink preview && echo "已完全符合期望, 无需部署"
dotlink preview || dotlink apply    # 仅在有变化时才部署
```

## 输出契约

每条目一行, 前缀为 `<序号>/<总数>`, 后接状态 token, 再跟着用户书写的目标路径与人类可读说明:

```text
1/4 create   ~/.bashrc           未部署 -> 已创建链接
2/4 ok       ~/.zshrc            已是最新
3/4 conflict ~/.gitconfig        冲突占用 (普通文件, 未覆盖; 该条目 on_conflict = "skip")
4/4 missing  ~/.config/nvim      源缺失 (仓库中不存在: nvim)
```

末尾一行汇总. 四项计数**互斥**, 相加恒等于总条目数:

```text
4 个条目: 1 成功, 1 已是最新, 1 未处理, 1 失败
```

各 token 归入哪一列是确定的, 实现必须按下表归类, 不得自行发挥:

| 汇总列 | 计入的 token |
|--------|--------------|
| 成功 | `create`, `replace`, `undo`, `restore` |
| 已是最新 | `ok` |
| 未处理 | `conflict`, `skip`, `foreign`, `absent`, `wrong` |
| 失败 | `missing`, `fail` |

据此上例为: 1 成功 (`create`) + 1 已是最新 (`ok`) + 1 未处理 (`conflict`) + 1 失败 (`missing`) = 4, 与总条目数一致.

列名是 token 的分桶名, 不是对动作的陈述: "未处理"这一列同时收容"有意不处理"的 `conflict` / `skip` 与"没有动作可执行"的 `foreign` / `absent` / `wrong`. 后三个 token 出现在只读命令 (`status`) 上, 那里根本没有"跳过"可言, 若把列名写作"跳过"会误导读者以为工具主动放弃了一项动作. `data-model.md` 的 `Report` 节与 `tasks.md` 的 T010 使用同一列名.

`missing` 计入"失败"而非"未处理", 因为它表示清单声明了一个仓库里不存在的源, 属于需要用户修正的配置缺陷, 与"目标被占因此有意不处理"的 `conflict` / `skip` 性质不同.

### 状态 token 表 (可供断言)

| token | 对应的 `Current` | 出现于 | 含义 |
|-------|------------------|--------|------|
| `create` | `Absent` (Action `Create`) | apply 执行 / preview 预测 | 将建立/已建立链接 (含自动创建父目录) |
| `ok` | `LinkedCorrect` (全部命令) / `Absent` (undo) | 全部命令 / undo | 已处于期望状态, 无需动作. `undo` 下 `Absent` 意为"该路径本就没有本工具创建的链接" |
| `replace` | 冲突类 (Action `ReplaceAndBackup`) | apply / preview | 将备份现有内容并建立链接 |
| `conflict` | `LinkedWrong` / `ForeignFile` / `ForeignDir` / `ForeignLink` (Action `RefuseConflict`) | preview / apply | 目标被占用且该条目 `on_conflict = "skip"`, 有意不处理 |
| `absent` | `Absent` | status | 目标路径不存在 (条目未部署) |
| `missing` | `SourceMissing` | 全部命令 | 源条目在仓库中不存在 |
| `foreign` | `ForeignLink` / `ForeignFile` / `ForeignDir` | status | 目标已被非本工具创建的内容占用, 附实际占用物 |
| `wrong` | `LinkedWrong` | status | 链接由本工具创建 (落在仓库内) 但指向的源不对, 附实际指向 |
| `undo` | `LinkedCorrect` / `LinkedWrong`, 同目录**无**备份 | undo | 已移除本工具创建的链接 (该条目无备份可恢复) |
| `restore` | `LinkedCorrect` / `LinkedWrong`, 同目录**有**备份 | undo | 链接已移除, 并从备份恢复了原内容 |
| `skip` | `ForeignLink` / `ForeignFile` / `ForeignDir` | undo | 该路径非本工具创建, 已跳过 (不删除) |
| `fail` | `Unreadable` (判定阶段的 lstat 故障), 或任意 (操作出错) | 全部命令 | 该条目无法处理 (附原因): 判定阶段读取失败, 或执行动作失败 |

**`Unreadable` 的 token 在各命令下都是 `fail`**: 它是判定阶段的**环境故障** (非 `NotFound` 的 `lstat` 失败, 见 `data-model.md` 3.1 的"求值语义"), 不随命令变化. 四命令的差异只体现在汇总列上 -- 对写入命令它是"尝试后失败", 对只读命令它是"本可报告却读不到". 二者同归"失败"列, 因此不另立 token (冒烟测试覆盖于 `tasks.md` 的 T057).

**`absent` 与 `missing` 不可混用**: `absent` 是"清单声明了, 但目标路径还没有东西" (`Current::Absent`); `missing` 是"仓库里找不到源条目" (`Current::SourceMissing`). 二者是不同状态, 必须分别断言.

**`conflict` 与 `foreign` 的分工**: 二者都描述"目标被非本工具内容占用"这一事实, 分别用于不同命令 -- `conflict` 是 `preview` / `apply` 视角 (强调"该条目 `on_conflict = skip`, 因此不处理"), `foreign` 是 `status` 视角 (强调"实际状态与清单要求的链接不符"). 同一 `Current` 在两条命令下用不同 token, 是刻意的: `status` 不该提动作策略, `preview` / `apply` 不该只说偏离而不说将怎么办.

### 必现信息 (FR-016)

- 备份发生的位置: `replace` / `restore` 行必须在说明中给出备份文件的完整路径.
- 失败原因: `fail` / `skip` / `conflict` / `missing` 行必须说明原因.
- 实际指向: `wrong` 与 `foreign` (当占用物是符号链接时) 行必须给出链接实际的指向.
- 占用物类型: `foreign` 行必须说明占用物是符号链接,文件还是目录, 因为只有"符号链接"这一情形会被 `undo` 视为不可移除.

## 命令语义细节

### `preview`
完全只读.对每条目输出"现状 + 将执行的动作".结论必须与随后 `apply` 的实际行为一致 (FR-017 / SC-006).不含任何交互提示.

### `apply`
逐条目执行 `classify` 给出的 `Action`.单条目失败不中断其余条目 (FR-014).幂等: 第二次运行所有条目为 `ok`, 且不产生任何文件系统改动 (SC-002).

### `status`
完全只读, 只报告现状, 不报告动作.用于发现"清单与实际不符".

### `undo`
仅处理本工具创建的链接, 即 `Current` 为 `LinkedCorrect` 或 `LinkedWrong` 的条目 (二者都意味链接落在仓库根内).其余情况一律 `skip` 并报告原因, 绝不删除 (FR-010) -- 尤其 `ForeignLink` (落在仓库外的链接) 必须 `skip`, 因为那可能是用户自己的配置.

移除链接后若同目录存在 `<原名>.dotlink-backup.*`, 恢复"最新"的一个并报告 `restore`; 无备份时报告 `undo`. "最新"是 `(时间戳, 消歧序号)` 的序: 先比 15 位时间戳, 同一秒内再比序号的**数值** (裸名视为 0, 故 `.10` 晚于 `.9`) -- 不是整名字典序, 序号 `10` 的字典序反而小于 `9`. 恢复先把链接原子移到同目录暂存名再复制备份就位, 复制失败时链接原样保留, 因此该条目可在下一次 `undo` 重试.

### `undo` 分支 (按 `Current` 取 token, 不得一概归为 `skip`)

| `Current` | token | 汇总列 | 是否触碰文件系统 |
|-----------|-------|--------|------------------|
| `LinkedCorrect` / `LinkedWrong`, 同目录**有**备份 | `restore` | 成功 | 是 (移除链接 + 恢复备份) |
| `LinkedCorrect` / `LinkedWrong`, 同目录**无**备份 | `undo` | 成功 | 是 (移除链接) |
| `ForeignLink` / `ForeignFile` / `ForeignDir` | `skip` | 未处理 | 否 |
| `Absent` | `ok` | 已是最新 | 否 |
| `SourceMissing` | `missing` | 失败 | 否 |
| `Unreadable` / 操作出错 | `fail` | 失败 | 否 (或仅部分) |

备份的有无决定 token 是 `restore` 还是 `undo`, 与 `Current` 是 `LinkedCorrect` 还是 `LinkedWrong` 无关 -- 后者只决定"是否允许移除", 前者决定"移除后是否恢复".

`Absent` -> `ok` 是本表的关键行: 它使"撤销后目标路径为空 (无备份可恢复, 或恢复后目标仍为空) 的清单上再次运行 `undo`"落入"已是最新"列, 因而满足退出码条件 2 并退 0. 若把它归入 `skip`, 第二次 `undo` 将退 1.

**幂等**: `undo` 是幂等的 -- 重复运行不改变任何路径, 也不删除非本工具内容. 退出码随之分两种情形:

- **无备份可恢复 (或恢复后目标为空)**: 第二次 `undo` 时 `Current` 为 `Absent` (无链接), 报告 `ok` 并退 0.
- **曾恢复过备份**: 第二次 `undo` 时目标被恢复出的原内容占用, `Current` 为 `ForeignFile` / `ForeignDir` / `ForeignLink`, 报告 `skip` (未处理) 并退 1 -- 与下面"并存语义"一致, 该内容不会被删除或再次消费.

备份文件本身**不删除**, 只是不再用于恢复("消费"在本契约中意为"不再参与恢复", 而非"从磁盘移除"). 两种情形下第二次 `undo` 都不得产生任何文件系统改动.

**并存语义**: 若某条目曾有备份但链接又被手工替换成普通文件, `undo` 只 `skip` 该路径 (不删除手工内容), 也不消费备份 -- 恢复备份的前提是"我先移除了自己创建的链接".
