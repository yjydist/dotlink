# Design

## Context

`os::normalize` 的契约是"已存在的祖先段解析符号链接, 末段永不解析" (`path-normalization`). 这个契约对 `classify` 与 `undo` 是必需的: 目标路径的身份是链接自身, 不是它指向的对象. 但 `manifest` 的 V-5/V-9b/V-10/V-11 是**清单层的对象关系**检查, 需要回答"两个写法是否指向同一对象"以及"谁包含谁". 只用词法形态会漏掉两种结构:

- 父目标的末段是符号链接, 子目标的祖先段被解析到链接的 referent, 于是嵌套关系在比较中消失.
- source 本身是符号链接, 其 referent 指向 target, 但 lstat 身份与 target 不同, 自指环不被发现.

已复现的后果见 proposal.md.

## Goals / Non-Goals

**Goals:**

- 让清单校验在"词法形态"之外拥有一致的比较形态, 覆盖 V-5/V-9b/V-10/V-11.
- 保持运行时路径语义不变: `Entry.target_path` / `source_path` 仍是末段不解析的规范化路径.
- 拒绝"符号链接父目标 + 嵌套子目标"与"source 符号链接指向 target"的清单, 退出码 2, 零改动.
- 现有合法清单 (单一目标的符号链接父目录, 独立的多目标) 行为不变.

**Non-Goals:**

- 不把 `os::normalize` 改成解析末段; 不改变 `classify` / `undo` 的状态判定.
- 不禁止所有符号链接形式的 target 或 source; 只拒绝与其它条目产生对象重叠的形态.
- 不解决并发修改造成的 TOCTOU; 不引入锁或事务.
- 不改变 V-11 的"多个独立目标可以共享同一源"语义.

## Decisions

### D1. 新增只读比较形态, 与运行形态分离

在 `src/os/mod.rs` 增加一个只读 helper (例如 `comparison_form(path) -> PathBuf`), 在现有 `normalize` 的结果上继续解析末段符号链接链, 复用 `Resolver` 的深度上限与词法回退.

备选方案: 直接让 `normalize` 解析末段. 否决理由: 会破坏 `classify` 对 `Absent` / `LinkedCorrect` / `ForeignLink` 的区分, 也会让 `undo` 找不到自己的链接. 备选方案: 用 `Path::canonicalize`. 否决理由: 要求路径存在, 悬空链接会返回错误, 与现有非严格 realpath 契约冲突.

### D2. V-5/V-9b/V-10/V-11 使用双形态

清单校验为每个 target/source 同时保存 `(lexical, comparison)` 两套路径. 字符串祖先/相等判定, 身份映射与祖先身份检查都在两套形态上执行; 任一形态命中即拒绝.

- V-5: 目标去重表按双形态建立; 两个目标只要在任一形态上相等或身份相同即冲突.
- V-9b: 每个基准点保存 lstat 与 follow 两种身份; 落点的 lstat 身份命中任一身份即视为命中. 这覆盖 HOME/manifest 自身是符号链接, 用户写成该符号链接路径的大小写别名的情况.
- V-10: source 的 follow 身份与链接文本解析目标加入自指判定.
- V-11: 目标祖先/后代, 目标与源重叠, source 祖先身份都按双形态与双身份执行.

实现上优先建立 `HashMap<PathBuf, usize>` / `HashMap<FileIdentity, usize>` 的两份索引, 保持现有 O(N * depth) 的复杂度; 不引入两两比较.

备选方案: 只对 V-11 做双形态. 否决理由: V-5 的重复目标与 V-10 的自指也需要同一比较口径, 否则同一对象在不同规则下结论不一致. 备选方案: 在 `Entry` 里保存比较形态并让所有命令使用. 否决理由: 运行时应只看到一个路径形态, 多存一份容易在后续调用点误用; 比较形态应留在 `manifest` 校验内部.

### D3. source 符号链接使用 follow 身份与解析目标

source 的 lstat 身份只代表链接对象本身. 校验时同时取 `basis_identity(source_path)` (follow), 并在 source 是符号链接时读取其链接文本, 解析为绝对路径后与 target 的双形态比较. 只要 target 等于该解析目标, 或位于其祖先/后代关系内, 即拒绝.

备选方案: 直接拒绝任何符号链接 source. 否决理由: 仓库内用符号链接指向共享配置是合法用法; 只应拒绝产生对象重叠的清单. 备选方案: 只在运行时报 `status` 异常. 否决理由: 清单校验的职责就是在任何改动前拒绝可静态发现的重叠, 且 `apply` 之后清单可能失效.

### D4. 错误说明保留可对照的书写形态与实际比较路径

新增拒绝面必须指出条目下标, 用户书写的 `source` / `target`, 以及命中的比较路径. 这样用户可以判断: 是清单写错, 还是符号链接父目录导致目标落到了别处.

### D5. 测试覆盖两个已复现结构与别名边界

- 符号链接父目标 + 嵌套子目标: 清单被拒绝, 退出 2, 四个命令都零改动.
- source 符号链接指向 target: 清单被拒绝, 退出 2, 零改动.
- 符号链接 target 与 referent 同时作为 target: V-5 拒绝.
- HOME 或 manifest 是符号链接时的别名落点: V-9b 拒绝.
- 合法的单一目标位于符号链接父目录下 (没有父目标条目): 清单仍被接受.

## Risks / Trade-offs

- [新增拒绝面是兼容性收紧] -> proposal 标为 **BREAKING**, README 与规格同时说明; 旧清单被拒时退出 2 且零改动, 不会产生半完成状态.
- [比较形态可能引入额外 lstat] -> 只在清单校验阶段计算, 每个路径常数次, 不进入 `classify` 热路径; 与现有 V-9/V-11 的身份检查同量级.
- [符号链接环可能让比较形态变慢] -> 复用现有深度上限 40 与词法回退; 达到上限后返回词法结果, 与 `normalize` 一致.
- [误拒绝合法的"父目标符号链接 + 子目标"清单] -> 这是 V-11 明确要拒绝的嵌套目标; 若用户确实想部署父目录和子项, 应先取消父目录条目, 改为逐项声明. README 给出替代写法.
- [source 符号链接指向 target 的判定依赖链接文本] -> 链接文本在清单校验与 apply 之间可能被外部修改; 这是已知并发窗口, 校验只覆盖静态可发现的情况.

## Migration Plan

无数据迁移. 已有链接与备份不受影响. 回滚方式是还原 `manifest` 校验与 `os` helper 的提交; 已部署文件系统不需要修复. 旧清单如果因为新增拒绝面而失败, 用户需要调整 target/source 写法, 参考 README 的嵌套目标替代写法.

## Open Questions

- 是否需要在错误说明中同时展示词法形态与比较形态, 还是只展示命中的那一侧? 当前按 D4 展示书写形态与命中路径, 可在实现时按可读性调整措辞, 不改变规格.
