# Design

## Context

`backup::copy_to_staging` (`src/backup.rs:236-251`) 用一个 `for serial in 1_u64..` 循环同时承担两件事: 为暂存根选一个未占用的名字, 以及执行整棵树的复制. 循环唯一的成功条件是 `copy_object` 返回 `Ok`; 唯一的重试信号是 `Err(AlreadyExists)` (`src/backup.rs:246`). 但 `copy_object` (`src/backup.rs:254-288`) 会递归复制子项, 子项的 `create_symlink`, `DirBuilder::create` 与 `create_new` 都可能返回 `AlreadyExists`, 而 `copy_error` (`src/backup.rs:349-354`) 保留原 `io::ErrorKind`, 于是子项冲突与暂存根名冲突在调用点完全不可区分. 冲突持续时每次重试都从第 1 个子项重新开始, 序号递增但没有上限, 进程不返回. `restore_backup` (`src/backup.rs:215-234`) 通过 `copy_to_staging` 复用同一逻辑, 因此恢复路径也有同一问题.

现有测试 `backup_staging_chooses_another_name_without_touching_occupants` (`src/backup.rs:1358-1380`) 只覆盖"第一个暂存根名被用户文件占用, 换到 `.2.partial` 成功"; `a_copy_failure_cleans_only_its_own_partial_directory` (`src/backup.rs:1383` 起) 覆盖失败清理, 但失败原因不是 `AlreadyExists`. 没有测试能区分"根名冲突"与"嵌套冲突".

`src/os/mod.rs:151-226` 已有一套可借鉴的测试接缝: 线程局部 `Cell`, 守卫在 `Drop` 时恢复, 注入点只在 `#[cfg(test)]` 下编译. 本设计沿用同样的形态注入嵌套 `AlreadyExists`.

## Goals / Non-Goals

**Goals:**

- 让"暂存根名被占用"成为唯一可重试的失败原因, 并且只能由暂存根的排他创建产生.
- 嵌套复制的任何错误 (含 `AlreadyExists`) 在该次尝试内直接成为条目失败, 不换名字, 不重试.
- 暂存根名冲突的重试有固定上限, 超限时条目失败并给出已尝试次数.
- 失败清理的边界不扩大: 只删本次排他创建的暂存根, 根名被占用时不触碰占用者.
- 用测试接缝锁定"嵌套冲突只尝试一次"与"根名冲突最多尝试 16 次", 并保持既有正常路径测试全部通过.

**Non-Goals:**

- 不改变备份命名, 消歧序号, 发布方式 (`rename_noreplace` 加父目录同步) 与恢复流程.
- 不改变 `on_conflict` 语义, 退出码映射或报告格式; 条目失败仍是 `fail` 与退出码 1.
- 不解决同一目录内其他进程的并发写入, 不把复制变成事务, 不串行化并发调用.
- 不改变"暂存名不参与查找"与"备份不自动回收"的约定.
- 不为非 unix 平台增加新行为; 平台门禁与既有降级策略不变.

## Decisions

### D1. 先排他取得暂存根, 再递归填充; 用类型区分冲突来源

把 `copy_object` 的返回值从 `io::Result<()>` 改为模块私有的 `Result<(), CopyFailure>`, 其中:

- `CopyFailure::StagingNameTaken`: 当 `copy_object` 在创建**自己这次调用的目标名**时收到 `AlreadyExists` 就产生; `copy_to_staging` 只对最外层的调用把它解释为"暂存根名冲突".
- `CopyFailure::Fatal(io::Error)`: 其余一切错误, 包括读取源, 复制内容, 应用元数据, 同步, 以及子项递归中被包装后的 `StagingNameTaken`.

`copy_to_staging` 只把最外层调用返回的 `StagingNameTaken` 当作换名信号, `Fatal` 立即转成 `Error::EntryFailed` 并返回, 不再进入下一轮. 子项递归通过一个内部函数调用 `copy_object`, 并把子项得到的 `StagingNameTaken` 包装为带子项路径的 `Fatal`; 这样嵌套冲突在第一次尝试就被定性为致命错误, 而不是在循环里再次出现.

每一种对象类型的根取得方式都是排他的: 符号链接用 `create_symlink`, 目录用 `DirBuilder::create` (`recursive(false)`), 普通文件用 `OpenOptions::create_new(true)`. 现有代码已经如此, 本变更只把"根创建"与"递归填充"在错误分类上分开, 不新增系统调用, 也不依赖"先检查再创建".

备选方案 A: 保留单一 `io::Result`, 在 `copy_to_staging` 里按错误消息或错误路径判断是否根名冲突. 否决理由: 消息匹配脆弱, 路径比较要处理符号链接与不同平台的分隔符, 而且冲突路径本身可能被外部改写.

备选方案 B: 给 `copy_object` 增加 `is_root: bool` 参数, 在函数内分支. 可行, 但调用点忘记传参时又会退回"所有 `AlreadyExists` 都可重试"的旧行为; 用返回值类型让冲突来源在类型上显式可见, 调用点无法把它误当成同类错误, 更符合本缺陷的根因.

### D2. 尝试上限用常量 16, 并在超限说明中给出尝试次数

在 `src/backup.rs` 顶部与 `PARTIAL_SUFFIX`, `RESTORE_SUFFIX` 相邻处新增:

- `const MAX_STAGING_ATTEMPTS: u64 = 16;`

理由:

- 正常路径第一次尝试即成功; 同 pid 的中断残留通常只有 0 到 2 个, 16 个候选已留出充足余量.
- 根名冲突的尝试只做一次排他创建就失败, 不复制内容, 因此上限的主要成本是系统调用次数与可预测的失败时间, 不是整树复制的放大; 16 次尝试在人为占满名字的目录里也能在毫秒级收敛.
- 16 明显小于"不可接受的长等待"的量级, 同时避免把上限设成 1 而破坏既有"暂存名被占用时可换名"的文档化行为.
- 上限是常量而非配置项: 该值只影响冲突环境下的失败时机, 不需要第二个配置面; 若将来确有需要, 再连同场景与说明一起调整.

超限时返回的说明形如: `暂存名 {last} 连续 16 次尝试均被占用, 已尝试 16 次`. 说明包含最后一个候选名与次数, 用户据此可以清理占用物后重跑. 超限是环境问题而不是复制失败, 因此仍走 `Error::EntryFailed`, 不新增错误变体.

备选方案 C: 只保留一个错误变体来区分根名冲突, 例如新增 `Error::StagingNameTaken` 并把嵌套错误降级为普通失败. 否决理由: 改造面扩展到调用方与报告层, 而且有界性仍要单独实现; 现在的根因是重试判据过宽, 不是错误类型不够. 若只加变体而保留无界循环, 挂死仍在.

备选方案 D: 无限重试但每次打日志. 否决理由: 日志不解决挂死, 反而在挂死时放大 I/O 与输出.

备选方案 E: 只文档化, 不修复. 否决理由: 目录含挂载点时自然触发, 挂死不可接受.

### D3. 失败清理仍只作用于本次取得的暂存根

- 根名被占用时 (`StagingNameTaken`), 本次尝试没有创建任何对象, 清理步骤 MUST NOT 触碰该路径.
- 根已取得但填充或元数据阶段失败时, 沿用 `finish_copy` 的"尽力而为"清理, 只删本次创建的暂存根; 原对象与既有备份不做任何操作.
- 超限退出时同样没有本次对象可清理, 直接返回条目失败.
- `copy_to_staging` 成功返回后, 调用方 (`write_backup_at` 或 `restore_backup`) 才允许把暂存对象 rename 到最终名; 本变更不改变这一顺序, 也不改变"不发布最终名"的语义.

恢复路径复用同一函数: `restore_backup` 的 `copy_to_staging` 失败继续映射为 `RestoreError::NotLanded`, 调用方仍可安全地把暂存链接移回原路径; rename 之后的父目录同步失败仍映射为 `LandedButUnsynced`.

### D4. 嵌套 `AlreadyExists` 的测试接缝与断言

在 `src/backup.rs` 的 `#[cfg(test)]` 区域增加线程局部注入, 形态与 `src/os/mod.rs:172-211` 一致:

- `thread_local!` 分别保存启用标志 (`Cell<bool>`) 与注入计数 (`Cell<u32>`); 计数从 0 开始, 启用标志为假时表示未启用.
- 守卫函数 `fail_nested_child_copy()` 启用注入并返回守卫; `Drop` 恢复启用标志与计数, 避免并行测试互相影响.
- 注入点放在子项递归的入口 (即 `copy_to_staging` 之下的非根复制), 每次子项创建都返回 `AlreadyExists` 并把计数加 1, 直到守卫被丢弃. 测试在错误返回后读取计数并断言恰为 1: 若实现仍把嵌套冲突当作根名冲突重试, 计数会随轮次增长 (或在无界实现下直接挂死), 断言会稳定失败. 注入点不在暂存根创建处, 因此不会被 `copy_to_staging` 误判为根名冲突.

测试一 (嵌套冲突快速收敛): 目标目录含至少一个子项, 启用注入后调用 `write_backup_at`.
断言: 返回 `Err`; 错误说明包含失败子项而不是"暂存名被占用"的措辞; 注入计数恰为 1 (证明没有重试); 目录中没有最终名的备份; 没有本次的 `.partial` 残留; 原对象仍可读且内容不变.

测试二 (根名冲突有界): 预先用用户文件占满从第 1 个候选起的 16 个暂存名 (序列 1 为 `<pid>.partial`, 2 到 16 为 `<pid>.<n>.partial`). 调用 `copy_to_staging`.
断言: 返回 `Err` 且说明含"16"; 目录项数量不增加 (没有第 17 个候选); 16 个占用文件的内容与 inode 不变; 原对象未被读取破坏.

测试三 (正常路径回归): 现有 `write_backup_copies_files_and_leaves_no_partial`, `backup_staging_chooses_another_name_without_touching_occupants`, `restore_chooses_another_staging_name_without_following_or_merging_occupants` 等继续通过; 新增用例只占用 1 个候选, 断言仍能换到 `.2.partial` 并成功发布.

另有一个仅测试用的元数据失败接缝 `fail_metadata()`: 在 `apply_metadata` 入口注入错误, 用于覆盖 `backup-fidelity` 的"元数据阶段失败" Scenario; 注入同样使用线程局部的启用标志与计数, 断言恰为 1.

### D5. 正常路径的用户可见行为不变

本变更只重排 `copy_to_staging` 的判断结构, 不改变:

- 暂存名拼接: `unique_staging_suffix` 与 `<pid>.<serial><suffix>` 的生成规则.
- 首次尝试的序号 1 与后续序号 2, 3, ... 的候选顺序.
- 子项复制顺序 (仍按 `read_dir` 顺序), 元数据应用顺序 (扩展属性 -> 权限 -> mtime) 与同步调用.
- 成功后的 rename 与父目录同步, 以及恢复路径的 `RestoreError` 分支.

因此正常路径的用户可见行为 (命名, 内容, 权限, 时间, 报告) 不变; 变化只发生在冲突路径: 嵌套冲突由"换名重来"变为"条目失败", 根名冲突由"无界"变为"至多 16 次".

## Risks / Trade-offs

- **嵌套冲突从"可能重试成功"变成"立即失败"** -> 若子项冲突只是瞬时的 (外部进程短暂创建后删除), 以前的重试可能碰巧成功; 现在该条目失败. 这是有意的取舍: 重试无法区分瞬时冲突与持续冲突, 而挂死的代价更高; 失败说明给出子项路径, 目标未被修改, 用户可重跑. 需要在 README 的已知限制中说明.
- **上限 16 对极端目录偏小** -> 极端情况下 (同 pid 反复中断留下大量残留) 会多失败几次. 缓解: 说明给出已尝试次数与最后一个候选名; 残留可由用户清理, 常量可单独调整, 不影响其他行为.
- **错误措辞变化影响日志断言** -> 既有测试与脚本若匹配旧的"暂存名..."文案可能失败. 缓解: 正常路径文案不变; 仅新增冲突路径文案, 由 `cargo test --locked` 与 `./scripts/check.sh` 覆盖, 必要时只调整断言, 不改变文案语义.
- **清理仍是尽力而为** -> `remove_any` 失败时可能留下本次的 `.partial` 残留. 这是既有语义; 本变更不发布最终名, 不删除原对象; 残留不参与查找.
- **接缝只覆盖注入点** -> 线程局部注入模拟的是"子项创建返回 `AlreadyExists`", 不覆盖真实挂载点与名称折叠差异. 缓解: 接缝用于锁定重试判据, 真实触发条件在说明中标注为审查员假设, 未单独复现.
- **同一目录的并发写入仍不受保护** -> 本变更只保证自身重试有界; 外部进程持续制造冲突时, 结果是有界失败而不是挂死, 这已经是可接受的收敛.

## Migration Plan

无数据迁移, 不改变磁盘格式. 已有备份与 `.partial` 残留不受影响. 回滚时把 `copy_object` 的返回值恢复为 `io::Result`, 恢复 `copy_to_staging` 的无界循环并删除常量与接缝即可; 备份命名与发布逻辑没有变化, 回滚不涉及数据修复.

## Open Questions

- 16 是否需要在后续变更中按用户反馈调整; 当前把它作为常量并写进规格, 调整时需同时更新场景与说明.
- 是否需要一个显式的"清理本目录暂存残留"命令; 本变更不提供, 与"备份不被自动回收"的既有约定一致, 留待后续讨论.
