# Design

## Context

`fix-long-basename-handling` 已在清单层用 V-12 限制单段 basename 不超过 200 字节, 并有意把整条路径长度交给操作系统. 但工具的生成名都以完整目标路径为前缀追加后缀:

- 备份最终名: `<target>.dotlink-backup.<YYYYMMDDThhmmss>[.<n>]`
- 备份暂存名: `<target>.dotlink-backup.<YYYYMMDDThhmmss>.<pid>.<n>.partial`
- 恢复暂存名: `<target>.<pid>.<n>.dotlink-restore.partial`
- 替换/撤销暂存名: `<target>.<pid>.<label>[.<n>]`, 其中 `label` 为 `dotlink-replace.partial` 或 `dotlink-undo.partial`

`Entry.target_path` 已由 `entry::resolve_with` 产出一个规范化绝对路径 (祖先段解析符号链接, 末段不解析), 上列生成名直接基于它拼接. 因此路径字节数与单段 basename 字节数相互独立: basename 合规的动态路径, 完整路径仍可能逼近 PATH_MAX. 已在 Linux 上复现 4071 字节 target 的 `apply` 成功与 `undo` 的 `ENAMETOOLONG`. 动机与复现证据见 `proposal.md`.

约束: 仅支持 Linux 与 macOS; 不写状态文件; 校验必须先于任何文件系统改动; 现有命名, 查找与恢复语义保持不变.

## Goals / Non-Goals

**Goals:**

- 让所有被清单接受的完整目标路径, 在追加最长生成名后缀后仍落在平台路径预算内, 从而四条命令都能处理.
- 在清单解析阶段 fail-fast: 退出码 2, 零改动, 说明给出可定位的条目信息与具体字节数.
- 平台预算常量, 最长后缀预留与 V-12 的 200 字节预算集中在同一共享模块, 避免清单与命名逻辑各写一份.

**Non-Goals:**

- 不改变备份最终名, 暂存名, 恢复名或查找规则; 不实现截断, 哈希或映射文件.
- 不覆盖 PATH_MAX 之外的文件系统限制 (例如更小 PATH_MAX 的挂载点或网络文件系统), 这些仍在运行期由操作系统错误报告.
- 不重新设计 V-12 的 basename 预算; 本变更只增加完整路径维度.

## Decisions

### D1. 平台常量加最长后缀预留, 而不是只检查固定长度

预算为平台路径上限减去最长生成后缀预留:

- Linux: `PATH_MAX = 4096` 字节.
- macOS: `PATH_MAX = 1024` 字节 (来自 `<sys/syslimits.h>`).
- 最长后缀预留取 55 字节: 当前实际最长约为备份暂存名的 47 至 50 字节 (16 字节标记 + 15 字节时间戳 + `.` + 7 位 pid + 2 位序号 + `.partial`), 55 覆盖 `dotlink-restore.partial` 与实现细节变化.

条目接受条件为 `target_path.as_os_str().len() + 55 <= PATH_MAX`; 说明中报告的预算按 `PATH_MAX - 55` 给出. 常量放在与 V-12 相同的共享模块, 由 `manifest` 校验与命名侧测试共同引用.

备选方案: 只检查 `target` 字节数小于 4096, 不预留后缀. 否决理由: 这正是当前 bug, 4071 字节的 target 通过检查后在 undo 暂存时溢出.

备选方案: 分别按每个后缀计算四条命令的预算. 否决理由: 清单契约不应依赖当前动作; 取最长后缀可以保证任何动作都安全, 也让错误说明只需一个预算数字.

### D2. 在清单解析阶段 fail-fast

V-13 放在 `src/manifest.rs` 的 V-9/V-10/V-11/V-12 之后 (V-11 与 V-12 都是循环后的全量检查, 因此 V-13 也在其后), 与它们同属改动前校验. 这样同时命中受保护落点, 路径重叠或 basename 预算的清单仍先报原规则, 不因新增的路径预算改变既有报错优先级. 超限时整体拒绝, 退出码 2, 说明包含条目下标, `target` 书写形态, 解析后字节数与预算. 四个子命令共用同一入口, 因此 `apply`, `undo`, `preview`, `status` 都会在改动前拒绝.

备选方案: 只把暂存名改成与 basename 无关的定长名. 否决理由: 这能修 `undo` 的暂存失败, 但备份最终名仍以完整路径为前缀, 超长路径在备份发布时照样失败; 而且会改变命名与查找契约.

备选方案: 运行期在暂存或备份失败时只报告操作系统错误. 否决理由: 会留下 `apply` 成功而 `undo` 失败的残留, 正是本变更要消除的状态; 用户也无法预知哪些条目可用.

备选方案: 只警告不拒绝. 否决理由: 清单契约仍接受无法被四条命令处理的目标, 坏状态不变; 警告在非交互或批处理场景容易被忽略.

### D3. 与 V-12 共用预算模块并同时审计

平台常量, 最长后缀预留与 200 字节 basename 常量放在同一处, 并有单元测试断言"200 + 最长后缀 <= 255"以及"最长后缀 <= 平台预留". 实现顺序在 `fix-long-basename-handling` 之后, 复用后者引入的共享模块; 两条规则必须同时满足, 各自失败时分别报各自规则.

备选方案: 在 `manifest.rs` 内联常量. 否决理由: 命名侧测试无法引用同一数值, 常量漂移会让规格与实现不一致.

## Risks / Trade-offs

- [相对 target 的接受面依赖仓库位置] -> `target_path` 按仓库根解析, 仓库移动到更深目录后同一清单可能从接受变为拒绝. 说明给出解析后的绝对路径字节数, 并写进 README; 用户可改用绝对路径或缩短目录层级.
- [更小的文件系统在运行期仍可能报错] -> 平台常量按 Linux/macOS 的常见上限取值; 更小 PATH_MAX 的挂载点不在承诺范围, 常量集中便于后续调整.
- [预留字节估计不足或过度] -> 55 字节覆盖当前最长后缀并留有余量; 测试锁定最长后缀不超过预留, 变更命名时测试会先失败.
- [V-12 与 V-13 需同时满足] -> 两条规则维度不同但都在清单层拒绝; 组合用例确认错误优先级不被打乱, 文档同时说明两个预算.
- [规范化差异导致边界偏移] -> 使用与运行时相同的 `Entry.target_path` 计算字节数, 避免另写一套解析; 边界测试覆盖预算减一, 预算与预算加一.

## Migration Plan

无数据迁移. 超长 target 的清单需要缩短完整路径 (例如上移仓库, 减少目录层级或改用绝对路径), 否则被整体拒绝. 已部署的链接不受影响. 回滚只需移除 V-13 校验并保留共享常量, 旧版接受面即恢复.

## Open Questions

- 55 字节预留是否需要按平台区分; 当前两平台共用同一常量, 若后续出现更长的生成名, 同步更新共享常量与 `manifest-schema` / `backup-lifecycle` 即可.
