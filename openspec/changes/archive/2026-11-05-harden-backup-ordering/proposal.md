# Proposal

## Why

备份名使用本地时区时间戳, 而"最新备份"按时间戳字符串的字典序判定. 同一目标只要在不同 UTC 偏移下生成过备份 (切换 `TZ` 环境变量, 本地时区不可用时退化到 UTC, 或夏令时回拨导致本地时间重复), 两个时间戳就不在同一时间轴上, 字典序可能与真实先后相反; `undo` 因此会恢复较旧的内容, 这是数据安全问题, 必须修复.

已实测: `TZ=Asia/Shanghai` 生成 `rc.dotlink-backup.20261104T231719` (旧内容 OLD-A), 数分钟后 `TZ=UTC` 生成更晚的 `rc.dotlink-backup.20261104T151720` (新内容 NEW-B), `undo` 恢复的却是 231719. 缺陷链路: `src/backup.rs:378-401` (时间戳在本地时区与 UTC 之间退化), `src/backup.rs:442-446` (先比较时间戳字符串), `src/backup.rs:111-147` (`scan_backups` 取最大者), `src/lib.rs:273-338` (`undo` 消费这份"最新"). 现有注释 `src/backup.rs:380` 声称"退化只影响时间戳的字面值, 不影响任何不变量", 该断言不成立.

## What Changes

- 备份名时间戳统一改为 UTC, 仍是 15 字符的 `YYYYMMDDThhmmss` 形态, 使同一目标的全部新备份落在同一时间轴上, 字典序即时间序; 删除本地时区读取与 "本地不可用则退化到 UTC" 的分支, 改写 `src/backup.rs` 中不成立的注释.
- "取最新"的排序结构保持不变: 先比 15 位时间戳, 同一时间戳内按消歧序号的数值比较, 裸名视为序号 0, 最后以文件名兜底; 只把"时间戳可比较"的前提明确为 UTC.
- 从 `Cargo.toml` 移除 `time` 的 `local-offset` feature, 不再为时区查询引入平台特定代码与数据依赖; 无新增依赖.
- 已知限制写入 README 与 design: 时钟回拨 (NTP 校时或手动改表) 仍可能让时间序与真实先后不一致; 变更前产生的本地时区备份与新的 UTC 备份混放时排序可能不可靠, 建议用户清理旧备份, 不做自动迁移.
- 既有语义不变: 同秒消歧序号, 命名形态, 查找规则与"备份不自动回收"均不修改.

## Capabilities

### New Capabilities

无.

### Modified Capabilities

- `backup-lifecycle`: "备份名携带秒级本地时间戳" 改为 UTC 时间戳并删除 "退化只影响字面值" 的表述; "取最新按时间戳再按序号数值" 明确同一 UTC 时间基准下字典序即时间序, 保留序号数值比较与文件名兜底.

## Impact

- 代码: `src/backup.rs` (`timestamp` / `timestamp_at` 与相关注释), `Cargo.toml`, `README.md`.
- 测试: `src/backup.rs` 的时间戳与查找单测; 新增或扩展端到端用例, 通过子进程的 `TZ` 环境变量复现跨时区排序反转, 覆盖 `undo` 恢复较新内容.
- 依赖: `time` 仅移除 `local-offset` feature, 版本与其他依赖不变.
- 行为: 新备份名的字面时间从本地时间变为 UTC; 旧备份不被重命名, 不自动迁移; 报告格式与退出码不变.
- 平台: 不新增平台特定代码; 移除 feature 后反而减少平台相关的编译分支.
