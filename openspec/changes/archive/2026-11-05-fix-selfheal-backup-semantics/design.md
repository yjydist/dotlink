# Design

## Context

动机见 `proposal.md` 的 Why. 与实现有关的事实如下.

- `classify::action_for` 把 `Current::LinkedWrong` 固定映射为 `Action::ReplaceAndBackup`, 不受 `on_conflict` 约束 (`src/classify.rs:195-207`). 外部占用 (`ForeignLink` / `ForeignFile` / `ForeignDir`) 在允许覆盖时也导出同一个动作, 因此动作层不区分"自愈"与"外部替换".
- `apply::replace_and_backup` 先记录目标身份, 调用 `backup::write_backup`, 备份落定后再暂存, 复核并删除旧对象 (`src/apply.rs:75-94`). `write_backup` 使用固定标记 `.dotlink-backup.` 构造备份名 (`src/backup.rs:29-30`), 并且对符号链接复制链接本身而不跟随 (`src/backup.rs:258-261`).
- `undo` 在动手前用 `BackupFinder::find_latest` 为 `LinkedCorrect` 与 `LinkedWrong` 取快照 (`src/lib.rs:273-338`); 查找在同一目录扫描带 `.dotlink-backup.` 标记且后缀完整的名字, 按 `(时间戳, 序号)` 取最大者 (`src/backup.rs:111-147`, `src/backup.rs:442-446`).
- `preview` 对任意 `Action::ReplaceAndBackup` 调用 `backup::backup_path_for` 预测备份路径 (`src/lib.rs:188-191`), 该函数同样使用 `.dotlink-backup.` 标记.
- 因此自愈产生的链接备份与用户备份在文件系统上不可区分, 共享同一个"最新备份"序列; 这是 `undo` 恢复错误链接的直接原因.

约束: 备份命名是唯一的持久元数据 (不引入状态文件); 备份不自动回收; 外部占用的备份命名已经被规格与 README 固定; `preview` 必须与 `apply` 的结论一致; `LinkedWrong` 的分类结论与 token 词汇不变.

## Goals / Non-Goals

**Goals:**

- 让自愈备份在文件系统命名上与用户备份分开, 使现有"用户备份查找"天然忽略自愈备份.
- `apply` 的自愈路径继续先完整备份旧链接, 再删除旧链接, 再建立新链接; 备份失败时旧链接保留.
- `preview` 对 `LinkedWrong` 预测的命名空间与 `apply` 实际写入的命名空间一致, 包括同秒消歧规则.
- 保持外部占用的备份命名, token 词汇, 退出码语义, 备份不自动回收与无状态文件.
- 用单元测试与端到端测试锁定"自愈后撤销回到未部署态"与"用户备份优先于自愈备份".

**Non-Goals:**

- 不自动识别, 迁移, 改名或删除旧版本已经产生的自愈型链接备份.
- 不让 `undo` 清理自愈备份, 也不为自愈备份提供新的清理命令或开关.
- 不改变 `Current` / `Action` 枚举, 不新增 `SelfHeal` 动作, 不改变分类与报告 token.
- 不改变用户备份的时间戳格式, 排序规则, 暂存名规则与恢复流程.
- 不引入 xattr, sidecar 索引, 状态文件或新的备份目录.

## Decisions

### D1. 自愈备份使用同目录下的独立标记 `.dotlink-heal.`

自愈备份名采用 `<原名>.dotlink-heal.<YYYYMMDDThhmmss>`; 名字被占用时追加 `.<n>` (n 从 2 起), 与用户备份的消歧规则同构. 暂存名采用 `<原名>.dotlink-heal.<时间戳>.<pid>.partial`, 只有完整复制成功后才以原子不覆盖的 rename 发布最终名, 因此"先完整备份再删除旧链接"的既有顺序与完整性前提不变.

用户备份查找先要求名字中存在 `.dotlink-backup.` 标记, 再判断标记后的后缀是否是完整时间戳或"时间戳 + 序号". 自愈名字使用 `.dotlink-heal.` 标记, 通常根本不含用户标记; 即使原文件名本身包含 `.dotlink-backup.`, 最后一个用户标记之后的部分也一定包含 `.dotlink-heal.` 段, 不可能是完整后缀. 因此自愈备份不会被 `BackupFinder` 选中.

备选方案与否决理由:

- 保留 `.dotlink-backup.` 名字, 在备份上写 xattr 或 sidecar 标记: 否决. 扩展属性是尽力而为且跨平台不一致, 旧备份没有该标记, 符号链接备份也无法可靠携带可移植的标记; 引入 sidecar 又等于第二份状态.
- 保留旧命名, 让 `undo` 跳过"指向仓库内的符号链接备份": 否决. 规格明确允许替换别人的符号链接并备份链接本身, 这类备份也可能是用户想恢复的原始内容; 没有可靠依据区分两者, 跳过会静默改变正常恢复语义.
- 把自愈备份放到子目录或临时目录: 否决. 违反"备份与被覆盖对象同目录"的既有约定, 增加用户查找成本, 还可能跨设备 rename.

### D2. 用显式的 `BackupKind` 贯穿备份 API, 查找器固定只认用户命名空间

新增 `enum BackupKind { User, SelfHeal }`, 并把命名空间作为显式参数传入:

- `backup_path_for(target, kind)`
- `write_backup(object, kind)`
- `backup_candidates_at(target, stamp, kind)`
- 两个标记常量 (用户与自愈) 取代单一 `MARKER`; `scan_backups` 只使用用户标记.

`write_backup` 的内部实现共享同一条"构造候选名 -> 排他暂存 -> 完整复制 -> 原子发布 -> 父目录同步"路径, 不复制第二套备份逻辑. `BackupFinder` 不接受 `BackupKind`, 因为 `undo` 在任何情况下都只能查用户备份; 把"不可搜索自愈命名空间"变成类型与 API 上的事实, 比在调用点传标志更安全.

`apply` 与 `preview` 都从已经存在的 `state.current` 选择命名空间: `LinkedWrong` 选择 `SelfHeal`, `ForeignLink` / `ForeignFile` / `ForeignDir` 选择 `User`. 映射函数放在 `apply.rs` (例如 `backup_kind_for`), `lib.rs::preview` 调用同一个函数, 使 `backup` 模块不依赖分类类型. 这个选择只影响备份命名, 不改变动作, 不改变报告 token, 也不要求执行层重新判定目标类型.

备选方案与否决理由:

- 新增 `Action::SelfHeal`: 否决. 动作枚举与所有穷举分支, 报告渲染和测试都要改, 而对外可见的 token 仍是 `replace`; 为命名差异扩大改动面不划算.
- 在 `apply` 中读取目标的链接文本以推断是否自愈: 否决. 执行层 MUST NOT 自行重新判定, 且会在判定与执行之间引入第二套归属规则.
- 传一个 `bool`: 否决. 调用点可读性差, 两个布尔值容易写反; 具名枚举在测试与审阅中更明确.

### D3. `preview` 按现状选择命名空间, 时间戳仍在各自时刻计算

`preview` 的 `ReplaceAndBackup` 行现在按 `state.current` 决定预测路径的命名空间: `LinkedWrong` 用 `.dotlink-heal.`, 外部占用用 `.dotlink-backup.`. 命名空间的选择与 `apply` 共用同一个映射函数, 避免两处各写一份条件.

预测名仍按 `preview` 时刻的时间戳与占用情况计算, `apply` 执行时重新计算. 跨秒时字面时间戳可以不同; 若两次之间目录内容变化, 消歧序号也可能不同. 规格只要求命名规则一致, 这是既有且已文档化的边界.

备选方案与否决理由:

- 让 `preview` 输出通配模式而不是完整路径: 否决. 既有契约要求 `replace` 行给出完整备份路径, 用户与测试依赖该形态.
- 在解析清单时固定时间戳并传给执行层: 否决. `preview` 与 `apply` 是两次独立进程, 无法传递; 即使同一进程内固定, 也可能因等待而使用过期时间戳, 增加冲突概率.

### D4. `undo` 保持现有代码路径, 由查找器天然排除自愈备份

`BackupFinder` 只扫描用户标记, 所以自愈备份不会成为"最新备份", 也不会让 `undo` 认为存在可用备份. 其结果正好落在既有 token 映射上:

- 目标原本不存在, 自愈后只有 `.dotlink-heal.` 备份: 查找返回无用户备份, `undo` 移除链接, token 为 `undo`.
- 目标原本是用户文件且用户备份仍在: 查找返回该用户备份, `undo` 恢复它, token 为 `restore`; 自愈备份留在原地.

`undo` 的查找, 快照, 恢复与暂存逻辑无需改动; 只增加注释与测试, 说明为什么自愈备份不参与.

备选方案与否决理由:

- 自愈备份也参与查找, 但在恢复时优先选中用户备份: 否决. 无用户备份时仍会恢复链接, 这正是要修的缺陷; 而且"有无可用备份"的 token 判定应与恢复选择同源.
- `undo` 恢复后删除自愈备份: 否决. 违反"备份不被自动回收".
- `undo` 发现自愈备份时输出额外警告: 否决. 需要额外扫描并改变输出契约; 对修复数据选择没有帮助, 可作为后续独立能力.

### D5. 旧命名空间残留只做文档化的已知限制, 不做启发式自动处理

旧版本写出的自愈备份仍然叫 `.dotlink-backup.<时间戳>`, 与合法的用户备份同名形. 新代码无法仅凭名字或对象类型判断它是不是自愈残留, 因为用户也可能合法地拥有一个指向仓库内的符号链接并被备份.

处理方式: README 说明升级后旧残留可能继续被 `undo` 选中; 给出人工步骤, 先检查 (`ls -l`, `readlink`), 确认某份备份是旧链接而非用户内容后, 将其改名移开而不是直接删除; 若 `undo` 已经恢复了该链接, 用户确认后移除恢复出的链接, 再从较早的备份中人工复制或移动所需内容. 手工恢复符号链接备份时应使用保留链接本身的复制方式 (例如 `cp -P` 或 `mv`), 避免跟随链接复制到目标. 任何删除都要求用户确认, 文档不提供一键清理脚本.

备选方案与否决理由:

- 自动跳过所有"符号链接且指向仓库内"的旧备份: 否决. 会误伤合法的用户符号链接备份, 与 D1 的否决理由相同.
- 启动时自动把旧自愈备份改名为 `.dotlink-heal.`: 否决. 无法可靠识别, 改名会改变备份集合且可能与其他名字冲突; 自动改写用户文件系统也超出本变更的范围.
- 每次 `undo` 扫描并提示疑似残留: 否决. 无法可靠判定, 只会制造噪声; 用户可用 `readlink` 自行核对.

### D6. 测试按"命名空间 -> 选择 -> 端到端"三层锁定

- 命名空间层: 断言两种 `BackupKind` 的裸名, 消歧名与暂存名; 断言用户查找忽略自愈备份; 覆盖原文件名本身包含 `.dotlink-backup.` 的边界.
- 选择层: 断言 `LinkedWrong` 在 `preview` 与 `apply` 中都选择自愈命名空间, 外部占用都选择用户命名空间; 断言自愈备份失败时旧链接保留.
- 端到端层: 情形 A (目标原本不存在) 与情形 B (目标原本是用户文件且有更早备份) 各一条; 覆盖连续 `apply` 不再制造新的用户备份, `undo` 后状态与备份符合预期; `preview` 行给出的路径与 `apply` 实际备份同命名空间.

备选方案: 只保留端到端测试. 否决理由: 端到端失败难以区分问题出在命名空间构造, 命名空间选择还是撤销查找; 三层测试把失败面收窄, 单元测试还能覆盖跨秒与大目录等端到端不便构造的边界.

## Risks / Trade-offs

- **目录中出现两种备份命名空间** -> README 明确两者的来源与用途, 测试断言外部占用仍只产生用户命名空间, 降低误读.
- **自愈备份随每次 source 变更累积且不自动回收** -> 这是既有的"备份不自动回收"边界; 文档说明可用手工清理, 不提供自动回收.
- **旧版残留仍可能污染 undo** -> 无可靠的自动识别手段; 作为已知限制写入 README, 给出检查与人工恢复步骤, 不猜测用户意图.
- **新增的 `BackupKind` 参数可能在调用点写反** -> 共用一个从 `Current` 到 `BackupKind` 的映射函数; 单元测试分别断言两种命名空间的标记; 编译期穷举 `Current` 分支.
- **preview 与 apply 跨秒时时间戳不同** -> 既有规格允许, 只要命名规则一致; 文档与测试都按命名规则而非字面值断言.
- **自愈备份仍是符号链接** -> 这是"备份链接本身, 不跟随"的既有要求; 手工恢复时需区分 `cp -P` 与跟随复制, README 给出说明.
- **旧备份与新备份的手工清理边界** -> 文档不自动删除任何文件, 只建议改名移开; 用户保留最终决定权.

## Migration Plan

无数据结构或状态迁移. 升级后:

1. 新的自愈备份写入 `.dotlink-heal.` 命名空间; 外部占用的备份继续写入 `.dotlink-backup.` 命名空间.
2. 旧版本已经产生的 `.dotlink-backup.` 自愈备份留在原地, 新代码不会迁移, 改名或删除它们; 其行为按 D5 的 README 说明人工处理.
3. 回滚到旧版本时, 新版本产生的 `.dotlink-heal.` 备份对旧版本的查找器同样不可见 (旧查找器只认 `.dotlink-backup.`), 因此回滚不会让这些备份被误恢复; 这些备份成为需要人工清理的残留.
4. 验证: 先运行针对备份命名, `apply` 自愈与 `undo` 的测试, 再运行仓库的完整检查脚本; 端到端覆盖情形 A 与情形 B.
