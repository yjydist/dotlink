# dotlink Constitution

## Core Principles

### I. 深模块

- 每个功能首先作为独立库存在, 不直接实现在应用代码中.
- 模块的公开接口保持最小且语义明确. 接口是成本, 隐藏的复杂度是收益.
- 复杂度向下拉入模块内部, 不通过配置参数, 回调或调用顺序暴露给调用者.
- 优先设计 "小接口, 大功能" 的模块.
- 抽象必须有具体的, 非投机的理由.

### II. CLI 验证接口

- 每个可独立交付的功能库或服务组件, 提供一个轻量 CLI 适配器, 用于自动化验证和 agent 交互.
- CLI 接受文本输入, 产生文本输出, 支持 JSON 用于结构化交换.
- 内部模块不强制要求 CLI; 其正确性由单元测试和集成测试保证.
- CLI 是适配器, 不污染核心库的接口设计. 核心库不为 CLI 增加参数或分支.

### III. TDD (测试驱动开发, 不可协商)

- 所有实现遵循红-绿-重构循环:
  1. **红**: 先写一个失败的测试, 测试必须表达期望行为, 并确认失败.
  2. **绿**: 编写最小实现使测试通过, 不添加测试未要求的功能.
  3. **重构**: 在测试保持通过的前提下改进结构.
- 在编写任何实现代码之前: 单元测试已编写, 经用户验证并批准, 确认失败.
- 合同测试必须在实现之前完成.
- 禁止在测试之前编写实现代码.
- 禁止跳过红阶段直接写实现.
- 禁止在绿阶段添加超出测试要求的代码.

### IV. 代码即文档

- 命名表达意图, 不描述实现.
- 函数单一职责, 从名字就能理解其行为.
- 控制流通过结构自然表达, 不依赖注释解释.
- 代码的阅读顺序反映理解顺序: 从高层概念到低层细节.
- 如果一段代码需要注释才能理解 "它在做什么", 优先重构代码, 而不是添加注释.

### V. 最小注释

- 注释只用于解释代码完全表达不了的信息: 非显而易见的 "为什么", 外部约束, 警告, 设计决策理由, 代码无法表达的契约.
- 禁止用注释解释 "这段代码在做什么".
- 禁止用注释弥补糟糕的命名或结构.

### VI. 简单性与反抽象

- 初始实现最多使用 3 个项目. 更多项目需要文档化理由.
- 直接使用框架功能, 而不是包装它们.
- 禁止投机抽象, 未来预留, 猜测性功能.
- 每个抽象必须有具体的, 非投机的理由.

### VII. 集成优先测试

- 优先真实数据库, 而非 mock; 使用真实服务实例, 而非 stub.
- 合同测试必须在实现之前完成.
- 测试验证真实行为, 而不仅仅是隔离单元的逻辑.

### VIII. 持续精炼与双向反馈

- 规范, 实现计划, 代码之间必须持续进行一致性验证.
- 生产指标, 事故, 运维学习必须反馈到规范中, 成为下一轮生成的输入.
- 每次需求变更必须更新受影响的规范, 计划与任务.
- 歧义, 矛盾, 缺口应作为持续精炼过程的一部分被识别和处理.

## 实现前门禁

### 深模块门禁

- [ ] 公开接口是否最小且语义明确?
- [ ] 复杂度是否隐藏在模块内部, 而非推给调用者?
- [ ] 功能是否首先作为独立库存在?

### CLI 验证门禁

- [ ] 可独立交付的功能边界是否提供了轻量 CLI 适配器?
- [ ] CLI 是否支持文本输入输出, 并可选支持 JSON?
- [ ] 内部模块是否避免了强制 CLI?

### TDD 门禁

- [ ] 是否有失败测试先于实现?
- [ ] 测试是否经用户验证并确认失败?
- [ ] 实现是否仅为通过测试的最小代码?
- [ ] 重构是否在测试通过后发生?
- [ ] 合同测试是否在实现之前完成?

### 代码即文档门禁

- [ ] 命名是否自解释?
- [ ] 函数是否单一职责?
- [ ] 注释是否只解释 "为什么", 而非 "做什么"?
- [ ] 是否存在本可通过重构消除的注释?

### 简单性与反抽象门禁

- [ ] 是否使用 <=3 个项目?
- [ ] 是否直接使用框架功能, 而非包装?
- [ ] 是否存在投机抽象或未来预留?
- [ ] 每个抽象是否有具体, 非投机的理由?

### 集成优先门禁

- [ ] 是否优先使用真实数据库和服务实例?
- [ ] 合同测试是否已定义并先于实现?
- [ ] 测试是否验证真实行为?

### 持续精炼门禁

- [ ] 规范变更是否同步更新了计划和任务?
- [ ] 生产反馈是否回写到规范?
- [ ] 歧义, 矛盾, 缺口是否被识别并处理?

## 开发工作流

- 变更按 "规范 -> 计划 -> 任务 -> 实现" 的顺序推进: 需求先落到 `spec.md`, 再由 `plan.md` 与 `tasks.md` 承接; 缺少规范或计划的实现不得开始.
- "实现前门禁" 在生成实现计划时逐项核对, 并在进入实现前复查; 未通过的项必须修正规范或设计, 而不是在实现中绕过.
- 测试先于实现完成并确认失败 (见第三条, 第七条); 每个任务在任务清单中标注其覆盖的需求与验证方式.
- 变更完成后同步更新受影响的规范, 计划与任务 (见第八条); 规范与实现不一致本身即视为缺陷.

## Governance

- 本宪章取代其他实践约定. 与本宪章冲突的实现, 流程或工具配置无效.
- 修订程序: 通过 `/speckit-constitution` 提出修订; 修订必须说明变更理由, 影响范围与迁移方案, 经用户批准后生效.
- 版本策略: 语义化版本 (MAJOR.MINOR.PATCH). MAJOR 用于不兼容的治理变更或原则的移除与重定义; MINOR 用于新增原则或实质性扩展指导; PATCH 用于措辞澄清与非语义修订.
- 合规审查: 每次实现计划与每次代码审查必须逐项核对 "实现前门禁". 无法满足的门禁项必须记录在实现计划的 Complexity Tracking 中, 说明不可避免的具体理由与恢复方案, 否则不得进入实现.
- 歧义, 矛盾与缺口按第八条识别并处理, 处理结果回写到受影响的最上游文档 (规范优先于计划, 计划优先于任务).
