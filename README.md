# dotlink

声明式 dotfile 软链接管理: 用一份 `dotlink.toml` 描述"哪个源文件应该出现在哪个目标路径", 由 dotlink 负责建立软链接, 并在需要覆盖已有内容时先备份.

无配置面, 无状态文件, 无交互提示. 重复执行不会产生累积副作用: `apply` 第二次运行为全部条目报 `ok` 且不改动文件系统, `undo` 在撤销后目标为空且同目录没有完整备份可恢复的清单上同样为 `ok` 并退 0. 若目标为空但同目录有完整备份, `undo` 恢复该备份, token 为 `restore` 并退 1; 恢复不消费备份. 源路径缺失时 `undo` 报 `missing` 并退 1, 不触碰目标, 即使目标为空且同目录有备份. 若上一次恢复了备份, 目标被恢复出的原内容占用: 恢复出普通文件, 目录或仓库外链接时, 第二次 `undo` 报 `skip` 且不改动文件系统; 恢复出的内容本身是指向仓库内的链接时, 按归属规则再次报 `restore` (目标与备份内容保持不变, 退出码 1).

## 安装

获取源码后, 在项目源码目录运行:

```sh
cargo install --path . --locked  # 安装到 ~/.cargo/bin
```

要求 Rust 1.97 或更高; 受支持平台为 macOS 与 Linux. 安装完成后, dotlink 在你的 dotfiles 仓库中运行 (下节的 `~/dotfiles` 即该仓库).

## 快速上手

以仓库 `~/dotfiles` 为例, 四步即可完成部署:

> **命令在哪里运行**: 所有命令都在**存放 `dotlink.toml` 的那个目录**中运行, dotlink 不向上搜索父目录.

```sh
cd ~/dotfiles                        # 仓库根目录, 也是 dotlink.toml 所在处
mkdir -p shell nvim
printf 'export EDITOR=vim\n' > shell/bashrc
printf 'vim.opt.number = true\n' > nvim/init.lua
```

**1. 编写清单** `~/dotfiles/dotlink.toml`:

```toml
[[entry]]
source = "shell/bashrc"
target = "~/.bashrc"

[[entry]]
source = "nvim"
target = "~/.config/nvim"
```

`source` 是仓库内的相对路径, `target` 是期望链接出现的位置.

**2. 预览** 将要发生什么 (只读, 不改动任何文件):

```console
$ dotlink preview
1/2 create    ~/.bashrc           未部署 -> 将创建链接
2/2 create    ~/.config/nvim      未部署 -> 将创建链接
2 个条目: 2 成功, 0 已是最新, 0 未处理, 0 失败
$ echo $?
1
```

这里退出 1 表示有链接待创建; 其他情况下也可能表示冲突, 源缺失或失败, 需结合逐条结果判断.

**3. 部署**:

```console
$ dotlink apply
1/2 create    ~/.bashrc           未部署 -> 已创建链接
2/2 create    ~/.config/nvim      未部署 -> 已创建链接
2 个条目: 2 成功, 0 已是最新, 0 未处理, 0 失败
$ echo $?
0
```

**4. 验证链接生效**:

```console
$ dotlink status
1/2 ok        ~/.bashrc           已是最新
2/2 ok        ~/.config/nvim      已是最新
2 个条目: 0 成功, 2 已是最新, 0 未处理, 0 失败
$ echo $?
0
$ readlink ~/.bashrc
/Users/you/dotfiles/shell/bashrc
$ cat ~/.bashrc
export EDITOR=vim
```

`~/.config` 这类缺失的父目录会被自动创建. 想回到原状时执行 `dotlink undo`; 它不会删除 `apply` 自动创建的父目录, 详见"已知限制"的"`undo` 不清理自动创建的父目录".

## 清单格式

清单固定命名为 `dotlink.toml`. 顶层只允许 `entry` 键, 条目以 `[[entry]]` 数组表给出, 至少需要一条:

```toml
[[entry]]
source = "shell/bashrc"
target = "~/.bashrc"

[[entry]]
source = "shell/zshrc"
target = "~/.zshrc"

[[entry]]
source = "nvim"
target = "~/.config/nvim"

[[entry]]
source = "git/gitconfig"
target = "~/.gitconfig"
on_conflict = "replace_and_backup"
```

### 字段

| 键 | 必填 | 取值 | 默认 | 语义 |
|----|------|------|------|------|
| `source` | 是 | 非空字符串 | 无 | 仓库内的相对路径, 可以是文件或目录; 不接受 `~` 前缀, 绝对路径, 以及解析后落在仓库之外的路径 |
| `target` | 是 | 非空字符串 | 无 | 期望链接出现的位置, 规则见下 |
| `on_conflict` | 否 | `"skip"` 或 `"replace_and_backup"` | `"skip"` | 目标被外部内容占用时的策略 |

`on_conflict` 只约束目标被**外部内容** (非 dotlink 创建的链接, 普通文件或目录) 占用时的处置: `"skip"` (默认) 会保留占用物并把该条目标记为 `conflict`, 本次不动它; `"replace_and_backup"` 会先把占用物备份到同目录的 `<原名>.dotlink-backup.<时间戳>`, 备份落定后把占用物原子移入同目录暂存名并复核身份, 复核通过才删除暂存对象并建立链接. 备份文件的完整路径会打印在 `replace` 行里. 备份名中的时间戳是 UTC 的秒级时间, 形如 `20260101T000000`, 与进程的本地时区设置无关; 同一目标的全部新备份共享同一时间轴, 因此字典序即时间序.

目标自身或目录内的任意子项是**挂载点**时, `replace_and_backup` 的备份整体失败: 该条目报告 `fail`, 不复制挂载点之后的内容, 不发布最终备份名, 也不删除或修改原对象; 说明给出挂载点完整路径并提示先卸载或移走该挂载点. 复制失败后的清理与目录替换的删除阶段同样不跨挂载边界: 删除暂存目录前先复核挂载点, 发现时把暂存目录原子移回原路径 (移回失败则给出暂存路径), 删除过程中才出现的挂载点会让删除停止并保留暂存目录. Linux 使用设备号加 `statx` 的挂载标识, 因此能识别同一设备上的 bind mount; `statx` 不提供挂载标识时读取 `/proc/self/mountinfo` 并按最长挂载点前缀解析 mount id, mountinfo 也不可用时退回设备号. macOS 使用 `statvfs` 的 `f_fsid` 作为附加标识, `f_fsid` 不同即视为不同挂载; 取不到或为 0 时退回设备号. 退回设备号时同一设备上的挂载仍可能漏检, 属于已知限制.

目标被特殊文件 (FIFO, socket, 字符设备, 块设备或其他既非普通文件, 非目录, 非符号链接的对象) 占用时, 该路径不属于可备份的外部占用: `status` 报 `foreign` 并给出精确类型, `preview` 与 `apply` 报 `conflict` 并说明特殊文件不支持备份且不会覆盖, `undo` 报 `skip` 且不触碰它. 是否覆盖不取决于 `on_conflict`; 要在此路径部署链接, 必须先手工移走该特殊文件.

备份名分为两个命名空间: 外部占用使用 `<原名>.dotlink-backup.<时间戳>`, 本工具重建自己的错误链接时使用 `<原名>.dotlink-heal.<时间戳>`. 两者共享同一套时间戳与序号消歧规则, 但只有前者参与 `undo` 的备份查找.

指向错误的本工具链接**不属于**外部占用: 例如 source 改名后, 目标上的旧链接仍指向仓库内的旧路径, `apply` 会无视 `on_conflict` 把它备份到自愈命名空间后重建为指向新 source 的链接 (`replace` token, 说明为"本工具的链接指向错误"); 外部占用触发的替换仍使用用户命名空间. `preview` 会预测同一动作, 并按目标当前状态预测对应命名空间的备份路径; 命名与消歧规则与 `apply` 相同, 跨秒时字面时间戳可以不同.

升级前已产生的自愈备份仍使用旧命名空间, 可能继续被 `undo` 选中; 本版本不自动迁移或清理它们, 处理步骤见"已知限制"的"旧版自愈备份残留".

备份保留原对象的内容, 对象类型, 权限位, 修改时间 (mtime) 以及全部可设置的扩展属性. 扩展属性采用**尽力而为**策略: 文件系统不支持, 权限不足或内核保护导致某个属性无法设置时跳过该属性, 其余内容与元数据仍照常备份; 磁盘满等 I/O 错误仍使该条目失败. 不保留所有权. 本工具不单独承诺 ACL 保真: macOS 的 ACL 不经 `listxattr` 暴露, 因此不在复制范围内; 若平台把 ACL 暴露为扩展属性 (例如 Linux 的 `system.posix_acl_access`), 则随该属性一并复制, 但不构成跨平台承诺. 也不保留符号链接自身的元数据. 目录的 mtime 在其子项全部复制完成后设置. 备份复制, 复制失败清理与暂存删除都以已打开的目录文件描述符为相对基准递归, 子项以不跟随符号链接的方式判定与打开: 若某个目录项在判定为目录之后被替换为符号链接, 该条目失败, 不读取或删除链接目标的内容, 原对象保持原样. 静态存在的符号链接仍只复制或删除链接本身.

`undo` 恢复时应用该备份自身的权限, mtime 与扩展属性. 旧版本创建的备份没有保真元数据, 恢复后 mtime 是**备份时刻**而不是更早的原文件时间, 内容与权限不受影响. 恢复成功后备份文件仍留在原地, 不会被删除; 不再需要的备份需自行清理.

`undo` 只查找并恢复用户命名空间 (`<原名>.dotlink-backup.`) 中的完整备份. 查找只接受字段合法的 UTC 日历时间戳: 月在 01 至 12 之间, 日落在该月的真实天数内 (含闰年 2 月 29 日), 时在 00 至 23 之间, 分与秒在 00 至 59 之间. 字段非法的同名文件不参与取最新, 也不会被删除, 重命名或移动, 需要时请自行判断与清理. 自愈命名空间 (`<原名>.dotlink-heal.`) 的备份永远不会被选中, 也不会被恢复或删除, 因此自愈后撤销会回到自愈前的状态: 目标原本不存在时只移除链接, 目标原本是用户内容且其备份仍在时恢复该用户备份.

### `target` 的三种形态

| 形态 | 写法 | 解析为 |
|------|------|--------|
| 主目录 | `~/.bashrc` | 当前用户主目录下的 `.bashrc` |
| 绝对路径 | `/etc/hosts` | 原样使用 |
| 相对路径 | `link/bashrc` | 相对于清单文件所在目录, 即仓库根 |

三种形态可以混用. 报告中显示的是你在清单里写的原始字符串, 不是解析后的绝对路径, 便于逐行对照. 序号按总条目数的位数右对齐; target 按终端显示宽度补齐, 因此各行 token 与说明列保持对齐. 超长 target 不截断, 只让该行的说明列右移.

显示宽度只按码点计算, 宽字符数据取自 Unicode 17.0 的 `EastAsianWidth.txt` 中 `W` 与 `F` 两类: East Asian Wide / Fullwidth 码点计 2 列; CJK 相关区块与两个 emoji 整块 (`U+1F300-U+1F64F`, `U+1F900-U+1F9FF`) 按整块保留, 块内未分配的码点与文本呈现型 emoji (例如 U+1F321) 也计 2 列, 使将来分配的字符不必升级二进制; 组合记号区段 (`U+0300-U+036F`, `U+1AB0-U+1AFF`, `U+1DC0-U+1DFF`, `U+20D0-U+20FF`, `U+FE20-U+FE2F`) 与变体选择符 (`U+FE00-U+FE0F`) 计 0 列; 其余码点按其 East Asian 宽度计列 (多数 1 列, 整块区间之外的 East Asian Ambiguous 也在其中). 仍属近似之处: 不按字素簇分段, emoji ZWJ 序列与区域指示符按码点逐个累加, 区段之外的组合记号按其 East Asian 宽度判定 (因此 U+3099 这类 East Asian Wide 的组合记号仍计 2 列), 已转义的字符按字面文本计宽. 这些差异只影响补齐的空格数量, 不改变行内容, 转义形式, token 或退出码.

报告对控制字符 (C0, C1 与 DEL), U+2028, U+2029 以及 Unicode 17.0 中具有 `Default_Ignorable_Code_Point` 属性的全部码点做转义: 换行显示为 `\n`, ESC 显示为 `\u{1b}`, BEL 显示为 `\u{7}`, U+2028 显示为 `\u{2028}`, 软连字符 U+00AD 显示为 `\u{ad}`, 标签字符 U+E0041 显示为 `\u{e0041}`, 保证每条目恰占一行且不会向终端发送控制序列或改变视觉顺序. 转义只发生在显示层, 不改变清单解析, 路径解析, 链接建立或退出码; 正常路径仍与清单原文逐字一致. 实际指向按解析结果原样显示, 首尾空白不会被裁剪; 判定阶段的读取失败会给出失败侧的解析路径 (源侧失败给源路径, 目标侧失败给目标路径), 不以另一侧的路径代替. 目标路径重复的清单会被整体拒绝.

`~` 简写只认 `~/...` 与裸 `~` (裸 `~` 的落点是主目录本身, 会被下一段拒绝). 写成 `~.bashrc` (漏斜杠) 或 `~foo/bar` 会被整体拒绝 (退出码 2), 而不会静默落到仓库里建出一个名为 `~.bashrc` 的路径 -- 落点错误的清单必须报错, 不能假装成功.

落点本身也不得退化: 归一化后是文件系统根 `/`, 当前用户主目录本身及其祖先 (即主目录的祖先, 例如裸 `~`, 等价的绝对路径, 以及 `~/..` / `~//../x` 这类经 `..` 离开主目录的 `~` 写法), 仓库根本身或其祖先 (如 `.` / `..`), 清单文件自身 (`dotlink.toml`), 或该条目自己的 `source` 时, 整份清单都会被拒绝并指出条目 (退出码 2, 不做任何改动). `~` 写法只表达主目录及其之下的词法路径: 判定只按路径组件消去 `.` 与 `..`, 不解析祖先符号链接, 因此 `~/symlinked-dir/file` 这类指向主目录外部的符号链接子目录不因该规则被拒. 落点已存在时还会比较文件系统身份 (设备号与 inode): 大小写别名, firmlink 别名以及指向同一对象的其它写法同样被拒, 不会因为字符串不同而放行; 身份判等不可用时退回规范化字符串比较, 不因此拒绝清单. 每个基准点 (文件系统根, 主目录的书写形态与物理形态, 仓库根及其祖先, 清单文件) 同时保存 lstat 形态与 follow 形态的身份: 当 `HOME` 或清单文件自身是符号链接时, 落点写成链接自身的大小写变体或解析后的物理路径都会命中, 不会因为两种身份不同而漏判. 这些落点一旦被替换备份, 毁掉的是整个目录, 整个主目录, 源仓库乃至唯一配置源. `~/sub`, `/etc/hosts` 这类绝对路径与仓库内的相对 `target` 都不受影响.

主目录祖先保护是一次兼容性收紧: 旧版接受的 `~/..`, `~//../x` 与主目录父目录的绝对路径现在都会以退出码 2 整体拒绝 (零改动). 主目录之外的目标请直接写不在主目录祖先链上的绝对路径, 或改用主目录之下的合法落点.

`target` 的末段 basename 还受 200 字节预算约束: 计数使用 UTF-8 字节, 不是字符数或显示宽度. 超过时整份清单被拒绝 (退出码 2, 不做任何改动), 说明给出条目下标, 书写形态, 实际字节数与上限. 该预算为备份最终名, 备份暂存名, 恢复暂存名与 apply/undo 暂存名的固定后缀预留空间, 保证清单接受的每个目标都能被四条命令处理; 只创建链接的条目同样受此约束. 多字节文件名会更早触发: 67 个 3 字节 UTF-8 字符即 201 字节, 即使显示宽度只有 134 列.

`target` 的完整路径同样受平台预算约束 (V-13): 规范化后的绝对路径字节数加上生成名最长后缀的预留 (55 字节, 即最长审计后缀 50 字节加 5 字节余量) 不得超过平台 PATH_MAX. Linux 的 PATH_MAX 为 4096 字节, macOS 为 1024 字节, 因此目标完整路径本身的上限分别是 4041 与 969 字节. 超过时整份清单被拒绝 (退出码 2, 不做任何改动), 说明给出条目下标, 书写形态, 解析后的绝对路径, 实际字节数与预算. 相对 `target` 按仓库根解析, 所以同一份清单在较浅的仓库根下可能被接受, 仓库移动到更深目录后可能被拒绝. 末段 200 字节预算 (V-12) 与完整路径预算 (V-13) 必须同时满足, 各自失败时分别报各自规则.

### 源与目标必须相互隔离

同一清单的目标之间不能互为祖先或后代; 任一目标也不能与任一源路径重合, 包含或被包含. 比较以规范化后的路径组件为准, 多个独立目标仍可共享同一源. 违反时四条命令都会在改动前退出 2, 指出相关条目和路径.

路径比较同时使用两种形态. **词法形态**就是运行时看到的规范化路径: 祖先段的符号链接会被解析, 末段永不解析. **比较形态**是清单校验专用: 在词法形态之上继续解析末段的符号链接链, 使同一对象的别名形态在比较中重合. 比较形态只用于清单校验, 不会写回运行时路径; `apply` / `status` / `undo` 仍按"末段不解析"的路径判定目标本身. 两种形态任一指明重叠都会被拒绝, 文件系统身份也同时比较 lstat 与 follow 两种形态.

比较形态带来的新拒绝面:

- **符号链接父目标 + 嵌套子目标**: 第一个目标 `~/.config` 是符号链接, 第二个目标写在 `~/.config/nvim/init.lua` 时, 后者经链接解析到前者指向的目录之内, 两者会被判为嵌套并整体拒绝.
- **源符号链接指向目标**: 仓库内的 `source` 是符号链接, 其链接文本解析后等于该条目的 `target` 或位于 `target` 的祖先/后代关系中时, 建链会形成 `target -> source -> target` 的环或经源链接改写目标目录, 整体拒绝.
- **符号链接目标与 referent 同时作为目标**: 一个条目把符号链接本身写成目标, 另一个条目写成它解析后的同一对象时, 两者会被判为同一个目标并整体拒绝.

这些拒绝面是一次 **BREAKING** 兼容性收紧: 旧版会接受的上述清单现在会以退出码 2 整体拒绝 (零改动). 若确实需要部署父目录和子项, 应取消父目录条目, 改为逐项声明互不嵌套的目标, 或先移除符号链接父目录再按真实路径声明; 源符号链接则应改为指向仓库内的普通文件, 或把目标移到符号链接解析目标之外.

这也是一次兼容性收紧: 旧版接受的跨条目源目标重合及嵌套目标清单现在会被拒绝. 例如同时部署 `nvim -> ~/.config/nvim` 和 `extra -> ~/.config/nvim/extra.lua` 会通过父链接修改源目录. 可以把额外文件直接整理到仓库的 `nvim` 目录中, 仅部署整个目录; 或取消目录条目, 改为逐文件声明互不嵌套的目标:

```toml
[[entry]]
source = "nvim/init.lua"
target = "~/.config/nvim/init.lua"

[[entry]]
source = "extra"
target = "~/.config/nvim/extra.lua"
```

源目标重合的条目则需把目标移到独立位置, 不再让部署目标兼任源文件.

### 未知键会被拒绝

顶层出现 `entry` 之外的键, 或条目里出现 `source` / `target` / `on_conflict` 之外的键 (例如把 `source` 拼成 `sorce`), 整份清单都会被拒绝并指出键名. 这是为了避免拼错的键静默退化成默认值.

## 命令与退出码

四条命令都不接受参数, 也没有 `--repo` / `--manifest` / `--force` 之类的开关: 仓库根与覆盖许可都写在清单里.

| 命令 | 作用 | 目标谓词 (达成才算成功) |
|------|------|--------------------------|
| `preview` | 只读: 报告每个条目将会发生什么 | 没有任何条目需要执行动作 |
| `apply` | 执行: 按清单建立链接, 必要时先备份 | 每个条目的目标路径都是指向其源条目的正确链接 |
| `status` | 只读: 报告清单与实际状态的不一致 | 清单与实际状态完全一致, 没有任何偏离 |
| `undo` | 撤销: 移除 dotlink 创建的链接, 并在存在备份时恢复; 目标为空但有完整备份时也恢复 | 每个条目的目标路径上都不存在 dotlink 创建的链接, 且本次没有从备份恢复任何内容 |

退出码的通用语义是: **退出 0 当且仅当该命令的目标已达成, 且没有遗留待办**. 两个条件必须同时成立.

`restore` 计入成功列 (恢复成功), 但它表示本次运行确实从备份恢复了内容, 因此不满足 `undo` 的目标谓词, 该条目会使退出码为 1. 成功列与退出码是两个维度, 不要因为退出 1 就把 `restore` 当成失败. 源路径缺失时 `undo` 只报 `missing` 并计入失败列, 不恢复目标侧的任何备份.

| 码 | 含义 (四条命令共用) |
|----|---------------------|
| 0 | 该命令的目标已完全达成, 且无遗留待办 |
| 1 | 存在未达成目标的条目, 或有被跳过 / 被拒绝 / 失败 / 源缺失的条目 |
| 2 | 清单校验失败 **或** 调用方式错误 (未做任何改动) |
| 3 | 平台不受支持 (仅支持 macOS 与 Linux) |

同一份"已部署好"的清单上, `apply` 与 `status` 退 0, 而 `undo` 退 1 -- 二者的目标刻意相反, 这是预期而非缺陷. `preview` 与 `apply` 共用同一套判断, 区别只在求值时刻: `preview` 在动手**之前**求值, 所以未部署时退 1; `apply` 在动手**之后**求值, 所以同一份清单上退 0.

`-h` / `-V` 是正常路径, 退出 0, 不属于上面四类结局.

标准输出与标准错误的写失败不改变退出码. 消费方提前关闭管道时 (例如 `dotlink status | head -1`), 报告可能只写出一部分, 进程不会 panic, 也不写诊断, 退出码仍按该命令的目标谓词与逐条结果计算. 其他标准输出写错误会尽力向标准错误写一行说明, 退出码不变. 标准错误本身不可写时, 说明静默丢弃, 退出码同样按该情形原本的结局计算 (清单错误仍是 2, 平台门禁仍是 3).

### 退出码 2 的两重含义

"清单校验失败"与"调用方式错误 (子命令缺失, 拼错或未知选项)"共用码值 2, 二者靠**标准错误的内容**区分:

清单校验失败 (含清单不存在, 当前工作目录不可用, 需要展开 `~` 时主目录无法确定):

```console
$ dotlink status
dotlink: 无法读取清单 ./dotlink.toml: No such file or directory (os error 2)
$ echo $?
2
```

不含 `~` 的清单不因 `HOME` 缺失被拒; 只有需要展开 `~` 时, 主目录不可用才是清单校验失败的原因, 与 `manifest-schema` 的"主目录解析"一致.

调用方式错误 (由 `clap` 在读取清单之前拒绝):

```console
$ dotlink statu
error: unrecognized subcommand 'statu'

  tip: a similar subcommand exists: 'status'

Usage: dotlink <COMMAND>

For more information, try '--help'.
$ echo $?
2
```

未知选项同样属于调用方式错误:

```console
$ dotlink status --json
error: unexpected argument '--json' found

Usage: dotlink status

For more information, try '--help'.
$ echo $?
2
```

判据是"标准错误是否为用法说明": 同时含 `error:` 与 `Usage:` 的是调用方式错误 (具体短语可以是 `unrecognized subcommand` 或 `unexpected argument`), 单行的 `dotlink: ...` 说明是清单本身有问题. 这两类都在读取清单之前被拒绝. 同样的说明写在每个子命令的 `--help` 里. 帮助文本是纯文本, 不含 markdown 强调符; 退出码段落与 `set -e` 脚本示例保持可读.

## 在 `set -e` 脚本中使用

退出 1 既可能表示有待办, 也可能包含跳过或失败的条目. 保留逐条输出, 并区分 1 与清单错误 2, 平台错误 3. 以下示例在 `preview` 退出 1 时尝试部署, 将最终结果交给 `apply` 判断:

```sh
set -e
if dotlink preview; then
  echo "已完全符合期望, 无需部署"
else
  dotlink_code=$?
  case "$dotlink_code" in
    1) dotlink apply ;;
    *) exit "$dotlink_code" ;;
  esac
fi
```

`undo` 会直接执行撤销, 成功移除链接也可能退出 1. 只调用一次, 查看逐条结果, 并保留原退出码供调用者判断:

```sh
set -e
dotlink_code=0
dotlink undo || dotlink_code=$?
case "$dotlink_code" in
  0) echo "无需撤销" ;;
  1) echo "请检查上方结果: 已执行撤销, 或有跳过, 源缺失或失败的条目" ;;
  2) echo "清单校验或调用方式错误" ;;
  3) echo "平台不受支持" ;;
esac
exit "$dotlink_code"
```

## 平台

仅支持 macOS 与 Linux. 在其他平台上, 任何参数解析与清单读取**之前**就会拒绝: 标准输出为空, 标准错误输出一行 `dotlink: 不支持当前平台 (仅支持 macOS 与 Linux)`, 退出码 3, 不触碰文件系统.

Windows 上的运行时拒绝**未在任何环境验证** (`cargo check --target x86_64-pc-windows-gnu` 只能证明源码可编译, 不能证明运行时行为).

生成备份名不读取本地时区: 时间戳固定为 UTC, 因此容器或缺少 tzdata 的环境不影响备份命名.

## 开发

要求 Rust 1.97 或更高 (edition 2024), 并安装当前工具链的 `rustfmt` 与 `clippy` 组件. 开发工具链由 `rust-toolchain.toml` 固定为 1.97.0, MSRV 仍为 1.97; 首次在该目录运行 `rustup` 或 `cargo` 时会按需安装对应工具链与组件. 运行本地完整检查:

```sh
./scripts/check.sh
```

脚本自动定位项目根目录, 最先运行 `scripts/check-punctuation.py` 检查非 ASCII 标点及其回归测试 `scripts/test_check_punctuation.py` (需要 Python 3, 仅用标准库), 然后依次执行格式检查, 全套测试, Clippy, 将警告视为错误的 rustdoc 构建和 release 构建, 任一步失败即停止. 标点检查覆盖 `AGENTS.md`, `README.md`, `openspec/config.yaml` (或 `config.yml`), `openspec/specs/`, `openspec/changes/`, `src/`, `tests/`, `scripts/` 与 `.github/` 中的自然语言与源码, 禁止 U+3000-303F, U+FF00-FFEF, U+2018-201F, U+2014, U+2026 与 U+00B7; 代码中确需这些字符时使用语言转义. `.github/` 当前不存在时扫描不产生额外开销, 保留该范围是为了将来加入 issue/PR 模板时自动纳入检查. 覆盖范围与退出码由 `scripts/test_check_punctuation.py` 在 `tempfile.TemporaryDirectory` 建出的临时目录中回归. 检查不修改源码; 构建产物位于 `target/`, 二进制为 `target/release/dotlink`. 脚本使用锁文件, 不安装工具链或交叉编译目标, 也不运行依赖审计: `cargo audit` 需要网络, 不属于本地检查或提交前置.

仓库不配置托管 CI, `./scripts/check.sh` 是唯一必需门禁: 推送前运行它即可, 检查项就是上一段列出的那些. 最低 Rust 版本与跨平台编译不在脚本内, 按紧随其后的既有命令块手工执行; 依赖审计同样不在脚本内, 需要时先安装 `cargo-audit` (例如 `cargo install cargo-audit`), 再按需运行 `cargo audit`. 删除托管 CI 后, Linux 上的自动执行与依赖公告监控改为维护者按需手工完成: 发布前在 Linux 机器或容器中运行 `cargo test --locked` (或在其中运行 `./scripts/check.sh`), 升级依赖或发布前运行 `cargo audit`.

按需验证最低 Rust 版本及跨平台编译 (需事先通过 `rustup` 安装对应工具链和目标):


## 已知限制

- **并发**: 同一清单上的写入命令已串行化. `apply` 与 `undo` 在执行前对 `dotlink.toml` 的文件描述符取排他 `flock`, `preview` 与 `status` 取共享 `flock`; 锁在整条命令执行期间持有, 不新建锁文件或状态文件. 平台或文件系统不支持 `flock` (`ENOTSUP`, `EOPNOTSUPP`, `ENOLCK`, `ENOSYS`) 时降级为不加锁并继续, 退出码与逐条结果仍只由清单与文件系统状态决定; 其他锁错误按清单读取失败处理 (退出码 2). 串行化只覆盖本地文件系统上的同一清单; 单次链接创建与不覆盖移动是原子操作, 但整个 `apply` / `undo` 仍不是事务; 替换期间目标可能暂时不存在, 多步操作可能部分失败. 并发修改源或父目录没有完整隔离, 备份开始后对目标的并发原地修改不会被该次备份捕获, 备份内容以复制时刻为准.
- **身份复核的基准是备份复制起点**: `apply` 在删除被替换对象前, 以原子不覆盖的 rename 把目标移入暂存名, 并复核暂存对象仍是备份实际复制的那个对象 (设备号, inode 与对象类型). 外部占用 (`Foreign*`) 条目在备份开始前被替换时, 替换后的对象会被备份, 因而允许替换 (`replace`); 备份完成后被替换的对象与基准不一致, 会被移回原路径并保留, 条目报 `fail` 且说明指出"备份时的对象与删除时的对象不一致". 复制起点的 `lstat` 与随后打开文件或读取目录之间仍有窄窗口, 极端并发下未能完全消除; 备份内容以复制时刻为准.
- **自愈备份前的归属复核**: `LinkedWrong` 自愈路径在写自愈备份之前会重新 `lstat` 目标, 并复核它仍是符号链接, 且解析后的链接目标仍落在仓库根内. 不满足时该条目报 `fail`, 目标原样保留, 不写自愈备份, 也不建立链接, 说明指出"判定之后目标已被替换为非本工具链接或内容"并提示重新运行. 复核把 `classify` 之后到备份之前的目标替换窗口收窄为一次 `lstat`, 但复核本身到备份复制开始之间仍有窄窗口; `apply` / `undo` 整体仍不是事务.
- **建链失败的恢复不是事务**: 替换末段建立链接失败时, `apply` 会立即从本次备份把原内容恢复到目标, 备份保留不消费, 该行仍报 `fail` 并给出备份路径. 恢复本身也可能失败 (例如目标被并发新建的内容占用): 此时并发内容保持原样, 原内容不在目标路径上, 只能从说明给出的备份路径找回.
- **`undo` 部分失败后的可重试性**: 移除暂存链接失败时, `undo` 先尝试把链接原子移回原路径; 移回成功则目标仍是可重试的链接, 下一次 `undo` 可再次尝试; 移回失败时保留暂存链接, 说明同时给出移除失败原因与暂存链接的完整路径. 恢复成功后的暂存清理失败不再静默: 该行报 `fail` 并给出残留路径, 恢复出的内容不回滚. 恢复失败说明给出所尝试的备份路径与失败原因, 回滚成功与失败两种收尾都保留该路径.
- **目标为空的恢复**: `undo` 在目标路径本就不存在且同目录有完整备份时恢复该备份 (token `restore`, 计入成功列但退出码仍为 1); 恢复不消费备份. 恢复出的内容若不是本工具创建的链接, 下一次 `undo` 报 `skip` 并退 1; 若本身是仓库内链接, 按归属规则再报 `restore` (restore-again), 目标内容与备份均不变.
- **非 UTF-8 路径按 lossy 显示**: 报告把路径转换为 UTF-8 供显示, 非 UTF-8 字节显示为 U+FFFD; 文件系统操作与备份查找仍使用原始字节, 因此目标末段含非 UTF-8 字节时, 其备份仍能被 `undo` 找到并恢复, 非 UTF-8 的无关目录项也不会影响其他目标. 清单本身必须是 UTF-8, 非 UTF-8 只可能出现在目录项.
- **`undo` 不清理自动创建的父目录**: `apply` 为建立链接创建的各级父目录在撤销后保留, 需要自行清理.
- **链接文本是绝对 source 路径, 仓库移动后无法自愈**: `apply` 直接把解析后的绝对 `source` 路径写入链接, 当前不使用相对链接文本. 仓库整体改名或移动后, 已存在的旧链接仍指向旧绝对路径; 该路径落在新仓库根之外, 按归属规则会被判为 `foreign`. `undo` 跳过这些链接 (不删除), 默认 `on_conflict = "skip"` 的 `apply` 也报 `conflict`, 工具无法自动修复. 移动仓库前请先执行 `undo`, 或移动后按报告手工清理旧链接再重新 `apply`.
- **目标 basename 上限 200 字节与运行期 NAME_MAX**: 清单校验按 UTF-8 字节拒绝末段超过 200 字节的目标 (退出码 2, 零改动), 而不是截断或哈希原名. 该预算与备份最终名, 备份暂存名, 恢复暂存名及 apply/undo 暂存名的最长后缀 (审计为 50 字节) 相加仍不超过常见文件系统的 NAME_MAX 255. 多字节文件名更早触发 (例如 67 个 3 字节字符已是 201 字节). 清单校验还会从目标路径向上寻找最近的已存在祖先, 读取 `statvfs` 的 `f_namemax`: 当末段字节数加 50 字节生成名预算超过该运行期上限时整体拒绝 (退出码 2), 说明给出条目下标, 实际字节数, 生成名预算与文件系统上限. 探测不到已存在祖先或 `statvfs` 失败时跳过该运行期检查, 仍按静态预算判定, 不因此拒绝清单.
- **目标完整路径预算**: 清单校验按 UTF-8 字节限制 `target` 的规范化绝对路径, 加 55 字节生成后缀预留后不得超过平台 PATH_MAX (Linux 4096 字节, macOS 1024 字节, 即完整路径上限 4041 / 969 字节). 它与 200 字节 basename 预算 (V-12) 必须同时满足; 各自失败时分别报各自规则. 相对 `target` 的接受面随仓库位置变化: 仓库移动到更深的目录后, 原本可接受的清单可能被整体拒绝. 更小 PATH_MAX 的挂载点 (例如部分网络文件系统) 仍可能在运行期报路径过长; 本工具不为这类挂载点另设更小预算, 也不做运行期 PATH_MAX 探测, 因为不存在可移植的只读接口. 运行期 NAME_MAX 只检查最近已存在祖先; 若该祖先与最终父目录分属不同文件系统, 预算可能偏保守, 但不会漏掉生成名超长的清单.
- **备份与暂存命名空间由本工具保留**: `<原名>.dotlink-backup.<时间戳>`, `<原名>.dotlink-heal.<时间戳>` 与 `.partial` 暂存名由本工具使用; 用户不应创建这些名字的对象, 它们会被视为备份或暂存占用.
- **备份不自动回收**: `undo` 恢复后备份文件仍留在原地, 更早的备份不会被自动使用或删除, 需自行清理; 复制中断留下的 `.partial` 残留也不会被 `undo` 消费.
- **备份持久性**: 备份的复制产物在发布最终名前同步到稳定存储 (普通文件与目录 `fsync`, rename 后同步父目录). 平台不支持同步时与扩展属性 / mtime 一样静默降级, 因此部分网络文件系统上仍不保证强持久性. rename 之后的父目录同步失败会使该条目失败, 但备份已发布, 说明会给出其路径; 恢复的父目录同步失败同样使该条目失败, 此时内容已就位且不会回滚.
- **备份的额外同步开销**: 每次替换备份都会对每个复制产物与父目录执行同步调用, 大型目录树的备份会明显变慢; 没有关闭开关.
- **暂存名冲突重试有界**: 所有暂存名 (备份根, 恢复根, `apply` 替换暂存名与 `undo` 撤销暂存名) 共用同一上限: 最多尝试 16 个候选名; 全部被占用时该条目失败, 说明给出已尝试次数与最后一个暂存名, 不创建第 17 个候选. 备份与恢复只在暂存根的排他创建失败时换名重试. `apply` 的替换暂存名形如 `<原名>.<pid>.dotlink-replace.partial`, 冲突时依次为 `<原名>.<pid>.2.dotlink-replace.partial`; `undo` 同理使用 `dotlink-undo`. 消歧序号一律位于 `.partial` 之前, 因此所有暂存残留都以 `.partial` 结尾.
- **受限 umask 下的目录备份**: 目录备份的暂存根在 `mkdir` 成功后立即 chmod 0700, 因此进程 umask 为 `0200` 或 `0777` 时仍可写入子项并完整发布备份. 失败清理会在删除暂存树前尽力恢复其中每个目录的 owner 读写执行权限, 避免已应用的只读源权限使本次创建的 `.partial` 目录无法清除; 该处理只作用于本次创建的暂存对象, 不触碰既有备份或用户文件.
- **预测备份名失败会如实报错**: `preview` 只在 `replace` 行预测备份路径. 若候选名的占用检测返回 `NotFound` 以外的错误 (例如父目录不可读的 `EACCES`, 或候选路径过长的 `ENAMETOOLONG`), 该行报告 `fail` 并给出底层原因, 不展示一个实际无法发布的预测路径; 其他动作不预测备份名, 不受影响. 清单校验的 basename 与完整路径预算使这类错误通常只在运行期环境变化时出现.
- **嵌套复制冲突直接失败**: 暂存根取得后, 递归复制中的任何错误 (包括子项创建时的 `AlreadyExists`) 使该条目直接失败, 不再换暂存名重试; 原对象与既有备份保持原样.
- **目录内特殊文件使备份整体失败**: 目标目录内含 FIFO, socket 或设备文件时, 整个备份失败; `apply` 报 `fail`, 说明给出该特殊文件的完整路径并提示先手工移走再重试, 不建立链接, 原目录与特殊文件保持原样. `preview` 只检查目标本身, 不递归预检目录内容, 因此仍可能预测 `replace`; 移走特殊文件后重跑 `apply` 即可.
- **目录内含挂载点使备份或删除失败**: `replace_and_backup` 不跨越挂载边界复制或删除. 目标自身或其后代是挂载点 (设备号不同, 或平台挂载标识不同) 时, 备份阶段即报告 `fail`, 不发布最终备份名, 挂载内容与目标保持原样; 备份完成后才出现的挂载点会在删除暂存目录前被拦截, 暂存目录尽量移回原路径, 移回失败时说明给出暂存路径, 删除过程中出现边界则停止删除并保留暂存目录. `preview` 只检查目标本身, 不递归预检目录内的挂载点, 因此仍可能预测 `replace`; 静态挂载点在备份阶段失败, 备份后出现的挂载点在删除前被拦截. 不识别 btrfs subvolume 等非挂载边界的文件系统子结构. Linux 优先依赖 `statx` 的 `STATX_MNT_ID` 识别同设备 bind mount, 旧内核或受限环境取不到挂载标识时回退到 `/proc/self/mountinfo` 的最长挂载点前缀; 两者都不可用时退回设备号, 同设备挂载可能漏检. macOS 使用 `statvfs` 的 `f_fsid` 作为挂载标识, 取不到或为 0 时退回设备号; 同一设备且 `f_fsid` 相同或不可用的 bind mount 与 nullfs 仍属于已知漏检边界. mountinfo 每个进程只解析一次, 运行中新增的挂载不在识别范围内. 处理方式: 先卸载或移走该挂载点再重试.
- **两侧都不存在的别名路径**: 身份判等要求落点存在; 目标与源都尚不存在, 或两个 target 都尚不存在时, 别名写法只按规范化字符串比较, 可能漏判. 在大小写不敏感或会做 Unicode 规范化的文件系统上, `~/.Foo` 与 `~/.foo` 这类仅大小写或规范化形态不同的两个 target 都会被清单接受; `preview` 报两个 `create`, 而 `apply` 按清单顺序建立第一条链接后, 第二条因 `EEXIST` 报 `fail`, 说明包含 `File exists`. 建链后由 `classify` 的链接归属复核接手, 属已知并发边界. 清单文件是符号链接时, 其解析后的最终文件已进入 V-9 保护面.
- **旧版自愈备份残留**: 本版本之前的 `apply` 把自己的错误链接按用户命名空间备份为 `<原名>.dotlink-backup.<时间戳>`, 与合法的用户备份同名形, 新代码无法仅凭名字区分, 也不会自动迁移或删除. 升级后可用 `ls -l <目录>` 与 `readlink <备份路径>` 检查: 指向仓库内旧路径的链接备份通常是自愈残留. 确认后把该备份改名移开而不是直接删除; 若 `undo` 已经恢复了这份旧链接, 确认后移除恢复出的链接, 再从更早的用户备份人工恢复内容. 手工复制符号链接备份时使用 `cp -P` 或 `mv`, 避免跟随链接复制到目标.
- **`undo` 只恢复最新用户备份**: 同目录下按"先比时间戳, 同一秒内再比消歧序号的数值"取用户命名空间中最新的完整备份; 时间戳是 UTC 的秒级时间, 定长 15 字符, 因此字典序即时间序. 自愈命名空间的备份不参与查找. 更早的备份保留但不被自动使用.
- **时钟回拨**: 备份的先后只由名字中的 UTC 时间戳决定. NTP 校时或手动改表使系统时钟回拨后, 新备份可能携带更早的时间戳, 仍会被误判为较旧; 本工具不做自动修正, 对顺序敏感时请在确认时钟稳定后再依赖 `undo` 的自动选择.
- **旧备份混放**: 本版本之前的备份名可能携带本地时区时间戳, 与本版本生成的 UTC 时间戳同形但可能不可比 (例如 `+08:00` 的名字比同一时刻的 UTC 名字大 8 小时). 同一目标的旧备份与新备份混放时, `undo` 的排序可能不可靠, 建议清理或归档旧备份; 本工具不自动迁移, 也不自动删除.
- **元数据保真为尽力而为**: 不保留所有权; 不单独承诺 ACL 保真 (macOS 的 ACL 不经 `listxattr` 暴露; 平台把 ACL 暴露为扩展属性时随该属性复制, 例如 Linux 的 `system.posix_acl_access`, 但不作跨平台承诺); 无法设置的扩展属性按属性跳过; 平台不支持扩展属性或 mtime 设置时静默降级, 不产生额外警告. 旧版本创建的备份按自身元数据恢复, 其 mtime 是备份时刻.
- **硬链接与稀疏结构不保留**: 备份按对象逐个复制内容, 硬链接被拆成独立副本, 恢复后不再共享 inode; 稀疏文件的空洞在读取时按普通数据复制, 恢复后不保证仍是稀疏文件. 它们与所有权, ACL 及符号链接自身的元数据一样, 不在 `backup-fidelity` 的保真范围内.
- **少数非 Default_Ignorable 的格式字符仍按原样显示**: 报告已转义 C0, C1, DEL, U+2028, U+2029 与 Unicode 17.0 中具有 `Default_Ignorable_Code_Point` 属性的全部码点 (例如 U+00AD, U+034F, U+061C, U+200B-200F, U+202A-202E, U+2060-206F, U+FE00-FE0F, U+FEFF, U+FFF0-FFF8 与 U+E0000-E0FFF), 包括软连字符, bidi 控制符与标签字符. 不具该属性的其他格式字符 (例如 U+0600-U+0605 与 U+06DD 这类 Prepended_Concatenation_Mark, 以及 U+13430-U+1343F 埃及象形文字格式控制符) 仍按原样显示, 可能造成视觉误读.

更多可执行验证场景见 [cli-contract 规格](openspec/specs/cli-contract/spec.md) 的 Scenario 与本文档的示例; 端到端验证流程已拆入各 capability 的规格.
